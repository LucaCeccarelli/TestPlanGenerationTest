# Extraction of formal and semi-formal artefacts from natural-language standards, and test-suite generation from those artefacts

Scope note: findings are reported so they transfer to any technical standard. The 18013-5/18013-6 figures are treated only as the measurement example. Where a source is secondhand (search-engine summary of a paywalled or image-only PDF) this is flagged explicitly.

## Q1. Published work extracting formal specifications, grammars, message formats or state machines from natural-language standards and RFCs, and its reported recall

### Takeaway
Four recent systems give directly comparable numbers, and they agree on a sharp pattern: **field/message-structure inventories are recovered at 90–100% recall, while constraints degrade badly (82% for independent constraints, 44% for dependent constraints at best, 16.7%/0% at worst), and state machines/transitions are worst of all.** The best-performing system (ParCleanse, ISSTA 2025) is also the one that commits to an explicit structural intermediate representation — a DAG of fields, types and constraints — rather than prose-shaped requirements.

### Cited Findings

**ParCleanse — "Validating Network Protocol Parsers with Traceable RFC Document Interpretation", ISSTA 2025 (Zheng, Xie, Shi, Wang, Zhang; DOI 10.1145/3728955)**
- Uses two explicit intermediate representations: a **DocTree** (hierarchy of RFC sections, used both to organise extraction and to trace findings back to document text) and a **format graph** (a directed acyclic graph of fields, types and constraints, used to generate test cases) — [alphaXiv overview of arXiv:2504.18050](https://www.alphaxiv.org/overview/2504.18050)
- Method: split RFC into sections; an LLM extracts a format from each section; each format passes a syntax check; sub-formats are merged bottom-up along the DocTree — [alphaXiv overview](https://www.alphaxiv.org/overview/2504.18050)
- Format-extraction precision/recall: **message types 100%/100%; field names 99%/95%; field types 94%/91%; independent constraints 98%/82%; dependent constraints 73%/44%** — [alphaXiv overview](https://www.alphaxiv.org/overview/2504.18050)
- Nine protocols including QUIC, DNS, HTTP/2 and MQTT, with implementations in C, Python and Go; **69 bugs detected, 68 previously unknown, 36 confirmed**; inconsistency-identification accuracy 97% — [alphaXiv overview](https://www.alphaxiv.org/overview/2504.18050). The ISSTA 2025 programme page states 35 confirmed, so the two figures disagree between versions — [ISSTA 2025 listing](https://conf.researchr.org/details/issta-2025/issta-2025-papers/77/Validating-Network-Protocol-Parsers-with-Traceable-RFC-Document-Interpretation)
- Test generation from the format graph: **positive and negative inputs come from property-level mutations, with the Z3 SMT solver producing concrete inputs** — [alphaXiv overview](https://www.alphaxiv.org/overview/2504.18050)
- Traceability loop: because the oracle derives from the RFC, each inconsistency maps back to DocTree sections; an LLM then diagnoses whether the cause is an implementation bug or an extraction hallucination, and if the latter, the format is refined and the process repeats — [alphaXiv overview](https://www.alphaxiv.org/overview/2504.18050)
- Outperformed ChatAFL on format extraction and found more bugs than ParDiff — [alphaXiv overview](https://www.alphaxiv.org/overview/2504.18050)
- A companion paper, "Large Language Models for Validating Network Protocol Parsers" (arXiv:2504.13515), uses a four-stage SpecAgent pipeline extracting a spec from RFCs (DocSpec) and from code (CodeSpec) and differencing them — [arXiv:2504.13515](https://arxiv.org/pdf/2504.13515)

**AUTOSPEC — arXiv:2511.17977**
- Five-stage pipeline: (1) an LLM labels each RFC section (state machine / overview / example / other) and assigns an action (extract / copy / summarize), and only "extract" sections proceed; (2) an LLM emits JSON fragments of states, commands, transitions and syntax/constraint rules, validated by a Pydantic model with one re-prompt on failure; (3) section-local graphs are filtered by a deterministic acceptance filter and merged into a protocol-level state-transition multigraph, from which **minimal transition paths (MTPs)** are computed; (4) MTPs are converted to an FSM skeleton, RFC excerpts are aligned to it, constraints added, output normalised; (5) a Fandango-based fuzzer runs the grammar against real servers and a repair agent classifies failures, localises the target rule, reduces the diff and emits minimal patches — [arXiv:2511.17977 (HTML)](https://arxiv.org/html/2511.17977v1)
- Output notation is an **I/O grammar** (interaction-aware, with `Client:`/`Server:` tags, semantic `where` constraint clauses beyond context-free, and a terminals block) — [arXiv:2511.17977](https://arxiv.org/html/2511.17977v1)
- Message-type recall: **client 92.8% average, server 80.2% average**; per protocol (client/server) POP3 100%/100%, SMTP 100%/63.6%, IMAP 83.3%/70.6%, FTP 80.6%/66.7%, ManageSieve 100%/100% — [arXiv:2511.17977](https://arxiv.org/html/2511.17977v1)
- Constraint recall: **independent constraints 16.7% average; dependent constraints 0.0%**. Precision: client 99.2%, server 94.3%, independent constraints 42.3%, dependent constraints 0.0% — [arXiv:2511.17977](https://arxiv.org/html/2511.17977v1)
- Message acceptance against real servers averaged **81.5%** (POP3 92.9%, SMTP 72.7%, IMAP 90.0%, FTP 80.6%, ManageSieve 71.4%); trace acceptance was lower (SMTP 57.1%, FTP 72.7%, ManageSieve 69.2%, IMAP 87.5%, POP3 90.0%) — [arXiv:2511.17977](https://arxiv.org/html/2511.17977v1)
- Baseline: naive LLM prompting **without** the RFC produced 0/5 syntactically valid grammars zero-shot, 2/5 few-shot, 3/5 with a command list, and **none were executable** — [arXiv:2511.17977](https://arxiv.org/html/2511.17977v1)
- Execution-guided repair ablation: largest deltas were FTP server recall −40.0% and POP3 server recall −33.3% without repair (table labelling is ambiguous; treat cautiously) — [arXiv:2511.17977](https://arxiv.org/html/2511.17977v1)
- AUTOSPEC does **not** detect or parse ABNF blocks. ABNF appears only in related work (HDiff). The paper does remark that reply types enumerated in ABNF were easier to recover, without explaining the mechanism — [arXiv:2511.17977](https://arxiv.org/html/2511.17977v1)
- Generality claim: five ASCII session protocols (SMTP, POP3, IMAP, FTP, ManageSieve) "without protocol-specific tuning"; binary, encrypted and real-time protocols (TLS 1.3, QUIC, SOME/IP) are future work; only I/O grammars tested as a target formalism — [arXiv:2511.17977](https://arxiv.org/html/2511.17977v1)

**Pacheco et al. — "Automated Attack Synthesis by Extracting Finite State Machines from Protocol Specification Documents", IEEE S&P 2022**
- Three-stage data-driven pipeline: word-representation learning for technical language; **zero-shot** mapping of protocol text into a **protocol-independent intermediate representation**; rule-based conversion of that IR into a protocol-specific FSM — [arXiv:2202.09470](https://ar5iv.labs.arxiv.org/html/2202.09470)
- The IR is an **XML annotation grammar** with definition tags (state, event, variable), reference tags, state-machine tags (transition, variable, timer, error, action) and control-flow tags; the authors describe it as "a general-purpose abstraction" that can "recover partial state machines" — [arXiv:2202.09470](https://ar5iv.labs.arxiv.org/html/2202.09470)
- BERT further pre-trained on **8,858 unlabelled RFCs (~475M words)**; six protocols evaluated leave-one-out (BGPv4, DCCP, LTP, PPTP, SCTP, TCP) — [arXiv:2202.09470](https://ar5iv.labs.arxiv.org/html/2202.09470)
- Best IR-extraction model (NeuralCRF) overall averages: token accuracy 64.42, weighted F1 64.18, macro F1 54.95, span-strict 68.81, span-exact 86.83. Rule-based baseline: 31.08 / 25.94 / 29.37 / 41.58 / 41.78 — [arXiv:2202.09470](https://ar5iv.labs.arxiv.org/html/2202.09470)
- Per-protocol strict/exact span (NeuralCRF): BGPv4 57.34/86.86, DCCP 75.60/93.25, LTP 74.22/94.41, PPTP 87.34/98.73, SCTP 58.54/65.85, TCP 59.82/81.90 — [arXiv:2202.09470](https://ar5iv.labs.arxiv.org/html/2202.09470)
- FSM level: the paper reports counts of correct / partially correct / incorrect / not-found transitions rather than precision/recall. Headline: about **17 of 20 canonical TCP transitions** recovered correctly or partially. Even with gold annotations not all expected transitions were extracted — [arXiv:2202.09470](https://ar5iv.labs.arxiv.org/html/2202.09470)
- **Of the residual errors in the gold-annotation FSMs, 67% (TCP) and 96% (DCCP) were attributed to information missing from, or ambiguous in, the document text** — [arXiv:2202.09470](https://ar5iv.labs.arxiv.org/html/2202.09470)
- Stated limitations: RFCs contain ambiguities and unspecified behaviours that human experts resolve, so a complete one-to-one mapping to canonical FSMs is not possible; properties must be hand-selected because RFCs do not state them; secure protocols (QUIC, TLS 1.3) not considered — [arXiv:2202.09470](https://ar5iv.labs.arxiv.org/html/2202.09470)

**3GPP-specific and benchmark work**
- **SpecGPT** (arXiv:2510.14348, Oct 2025) extracts protocol state machines from 3GPP documents: segments specifications into meaningful paragraphs, applies domain-informed prompting with chain-of-thought, and uses ensemble methods for reliability; evaluated on NAS, NGAP and PFCP against manually annotated ground truth, claiming to outperform existing approaches — [arXiv:2510.14348](https://www.arxiv.org/abs/2510.14348). **I could not retrieve its precision/recall/F1 table**; the abstract page carries no numbers.
- **PSMBench** (NeurIPS 2025) pairs **1,580 pages of cleaned RFC text with 108 manually validated states and 297 transitions across 14 protocols**, scored with structure-aware semantic fuzzy matching; reported trade-off is that larger LLMs have higher recall but over-generate while smaller models are more precise, with DeepSeek-V3 best on state-set F1 at **0.715**, and a persistent gap between state accuracy and transition accuracy — [PSMBench listing](https://mlanthology.org/neurips/2025/shen2025neurips-psmbench) (secondhand: these figures came from a search summary of the anthology page and NeurIPS slides, not from the paper PDF — verify before citing)
- **FlowFSM** (arXiv:2507.11222) uses prompt chaining and chain-of-thought over raw RFCs, starting from identifying relevant sections, isolating candidate commands, then synthesising structured state-transition information — [arXiv:2507.11222](https://arxiv.org/pdf/2507.11222)
- **Berserker** (arXiv:2107.01912) is the only system found that extracts a **real ASN.1 module** out of a standards document: it "extracts RRC ASN.1 schema definitions directly from a 3GPP TS and compiles the extracted RRC ASN.1 schema to produce corresponding encoder and decoder", working from the MS Word source of any 3GPP RRC TS for 4G and 5G, emitting the complete schema as a single plain-text file — [arXiv:2107.01912](https://arxiv.org/pdf/2107.01912) (extracted locally via ghostscript txtwrite)
- Berserker cites a pre-existing third-party extractor of the same kind: **OpenAirInterface's "ASN.1 extractor from 3GPP specifications" (2020), gitlab.eurecom.fr/oai/** — [arXiv:2107.01912](https://arxiv.org/pdf/2107.01912)

### Inferences
- The consistent split across all four systems — structure recovered well, constraints recovered poorly — is the strongest result in this literature for the tool's purposes. It predicts that an extraction pipeline aimed at the official suite's bulk (455 presence/absence + 257 type/encoding checks = 79% of the 907 cases) is operating in the high-recall regime, while the 97 value-domain checks sit squarely in the 44–82% constraint-recall regime and the 44 behaviour/flow checks in the worst (state-machine) regime.
- ParCleanse beating AUTOSPEC on constraint recall by a factor of ~5 (82% vs 16.7% independent) while using a comparable LLM-over-sections method suggests the difference is the **target representation**: a typed field/constraint DAG rather than a grammar with semantic side-conditions. Grammar notations force constraints into an awkward slot; a field-attribute record does not.
- Pacheco's finding that 67–96% of residual FSM errors come from information absent or ambiguous in the text sets a hard ceiling on prose-only extraction and is the strongest published argument for reading the embedded formal blocks instead.

### Gaps
- No SpecGPT numeric results obtained (abstract page only; PDF is image-based for WebFetch).
- No published work found that extracts **CDDL** from a document. Berserker (ASN.1 from 3GPP Word source) and rfcstrip/xym (YANG from RFC text) are the only document-to-formal-block extractors located, and neither reports a recall figure against a hand-built ground truth.
- No work found that extracts **X.509 certificate profile tables** from a standards document into a machine-readable profile.

## Q2. Established techniques for deriving a test suite from a formal data definition, and yield per field or per production

### Takeaway
The derivation machinery is old, well-defined and notation-independent: a coverage criterion over the definition (terminal / production / derivation / k-path for grammars; category-choice combination for field inventories) plus a mutation operator set that breaks exactly one rule at a time. Published **yields per element are not reported as ratios** anywhere I found; what is reported is total counts for a specific artefact, and the one clean figure is Ostrand & Balcer's 1944 test frames from a 7-category specification.

### Cited Findings

**Grammar coverage criteria (foundational, dated)**
- **Terminal symbol coverage**: every terminal symbol in the grammar appears in at least one test. **Production coverage**: every production rule is exercised; production coverage subsumes terminal symbol coverage. **Derivation coverage**: every string the grammar can derive — "except in special cases, this will be impractical", because a BNF grammar can contain infinitely many strings through recursive productions — [UVA CS 3250 syntax/grammar slides](https://cs.virginia.edu/~up3f/cs3250/slides/3250meet29-syntax-grammar.pdf); [UWA CITS5501 syntax-based testing](https://teaching.csse.uwa.edu.au/units/CITS5501//lectures/lect05c--mutation.pdf)
- **Purdom's algorithm (1972)**: "A sentence generator for testing parsers", *BIT* 12:366–375, DOI 10.1007/BF01932308 — a fast algorithm producing a **small set of short sentences from a context-free grammar such that every production is used at least once**, intended for testing parsing programs and debugging grammars, with experimental results on automatically generated SLR(1) parsers — [Springer](https://link.springer.com/doi/10.1007/BF01932308)
- Malloy and Power (2001) gave an interpretation of Purdom's algorithm for automatic test-case generation; Paracha's 2008 McMaster MSc thesis implemented it in Java and C++ for an LL(1) compiler grammar — [Springer / search trail](https://link.springer.com/doi/10.1007/BF01932308); [Paracha thesis](https://macsphere.mcmaster.ca/bitstream/11375/21291/1/Paracha_Asma_M_2008_12_master.pdf)
- **k-path coverage** (Havrikov, Kampmann, Zeller, "From Input Coverage to Code Coverage: Systematically Covering Input Structure with k-Paths"): covers individual syntactic elements **and their combinations up to depth k**; k=1 reduces to covering each symbol, k=2 requires each symbol in the context of all its parents; the authors report significantly higher code coverage than approaches that ignore input coverage — [CISPA publication record](https://publications.cispa.de/articles/journal_contribution/From_Input_Coverage_to_Code_Coverage_Systematically_Covering_Input_Structure_with_k-Paths/24612432)
- Parser-testing work uses production coverage as the yardstick and generates both positive and negative sentences, comparing Purdom's algorithm against the Grow algorithm — [Lučanin/Maleković, *Journal of Information and Organizational Sciences*](https://scindeks-clanci.ceon.rs/data/pdf/1821-3251/2014/1821-32511401069L.pdf)

**Syntax testing / anti-syntax (Beizer tradition)**
- "Data formats can be mechanically converted into many input data validation tests. Such a conversion is easy when the input is expressed in a formal notation such as BNF" — testing the normal condition uses a covering set of paths of the syntax graph; testing the garbage condition uses invalid input sets — [course material summarising Beizer's syntax testing](https://teaching.csse.uwa.edu.au/units/CITS5501//lectures/lect05c--mutation.pdf)
- Error cases are built incrementally: start from a covering set of correct strings, then **using the syntax definition graph as a guide, generate all single-error cases, then all double errors, triple errors, …** — same source
- Two cautions from the same tradition: random strings "get recognized as invalid too soon", and fully automatic garbage generation diverges ("you will be going down a diverging infinite sequence of syntax testing"), so single-rule violation is the practical stopping point — same source
- A tool prototype exists for this: **SYNTest: Prototype of Syntax Test Case Generation Tool**, IEEE — [IEEE Xplore 9310968](https://ieeexplore.ieee.org/document/9310968). I did not retrieve its method or numbers.

**Category-partition and classification trees (the field-inventory analogue of grammar coverage)**
- **Ostrand & Balcer, "The category-partition method for specifying and generating functional tests", CACM, June 1988, pp. 676–686**: the tester splits the specification into independently testable units, identifies the parameters and environment conditions that affect behaviour, finds the **categories** that characterise each, subdivides categories into **choices**, and a generator combines choices into **test frames**; constraints and error-case rules then prune — [Ostrand & Balcer 1988 PDF](https://faculty.cc.gatech.edu/~harrold/6340/cs6340_fall2009/Readings/ostrandCategoryPartition88.pdf)
- The paper's worked FIND example yields **4 × 3 × 3 × 3 × 3 × 3 × 2 = 1,944 test frames** before constraint pruning — [Ostrand & Balcer 1988](https://faculty.cc.gatech.edu/~harrold/6340/cs6340_fall2009/Readings/ostrandCategoryPartition88.pdf)
- **Classification Tree Method** (Grochtmann & Grimm, 1993) extends category-partition: **classifications** are the criteria for partitioning the input domain, **classes** the disjoint value subsets, organised into a hierarchical tree, with two phases (identify classifications and classes; combine classes across classifications into test cases). Class selection uses equivalence partitioning for abstract cases and boundary-value analysis for concrete cases. A known weakness is that "their tree construction method is rather ad hoc", producing tester-to-tester variation; Chen and Poon's classification-hierarchy table addresses this — [Wikipedia, Classification Tree Method](https://en.wikipedia.org/wiki/Classification_Tree_Method); [Chen/Poon technical report](https://i.cs.hku.hk/~tse/Papers/2000s/pictTR.pdf)

**Per-notation generators**
- **ASN.1 — Berserker's two-level strategy tables** (arXiv:2107.01912) are the clearest published example of enumerating a test matrix from a data definition. Table 1, mutations of the *schema*: change primitive data types (BOOLEAN, INTEGER, ENUMERATED, OCTET STRING, BIT STRING), change structured data types (SEQUENCE, SEQUENCE OF, CHOICE), **extend options** (add new options to ENUMERATED/SEQUENCE/CHOICE), **reduce options** (remove existing options), **scramble options** (reorder SEQUENCE/CHOICE), **change size** (alter upper/lower SIZE limits for INTEGER, OCTET STRING, BIT STRING, SEQUENCE OF). Table 2, per-type value strategies: INTEGER → random value within SIZE constraints; ENUMERATED → random option from the enum; BIT STRING → random bit series of random length within bounds; SEQUENCE / SEQUENCE OF / CHOICE → traverse to primitives and apply the corresponding strategy; **OPTIONAL (qualifier) → for mutation, remove an included field or include a missing field; for generation, randomly choose to include, and if included initialise with the corresponding strategy**; specific-name selection when several fields share a type; perturbation (out-of-order messages) in generation only — [arXiv:2107.01912](https://arxiv.org/pdf/2107.01912)
- Berserker also names the degenerate maximal case: "in a so-called **Christmas tree message, all optional fields are included**" — [arXiv:2107.01912](https://arxiv.org/pdf/2107.01912)
- **asn1tools** can emit a libFuzzer harness (`generate_c_source --generate-fuzzer`), but its C generator requires all types to have a known maximum size, and **`WITH COMPONENT`/`WITH COMPONENTS` constraints are ignored** (except for OER REAL); extension additions `...` are supported only in the OER generator — [asn1tools docs](https://asn1tools.readthedocs.io/)
- **asn1scc.Fuzzer** generates test cases from ranges: given an ASN.1/ACN model it produces values falling outside the accepted range, leaving delivery to the SUT and verdict assignment to the user — [n7space/asn1scc.Fuzzer](https://github.com/n7space/asn1scc.Fuzzer)
- A commercial **universal ASN.1 BER fuzzer test suite** exists (Black Duck/Synopsys Defensics) — [Defensics ASN.1 BER](https://www.blackduck.com/fuzz-testing/defensics/protocols/asn1-ber.html)
- **JSON Schema — Fences** (Python): "generates a set of valid samples which fulfil your schema. Additionally, it generates a set of invalid samples which intentionally violate your schema", and claims to generate samples **systematically instead of randomly** — [PyPI: fences](https://pypi.org/project/fences/) (quotes are from the package description surfaced in search; the PyPI page itself failed to render for me)
- **CDDL** has a working validator rather than a generator: **cddl-rs** parses CDDL for conformance against RFC 8610 and validates JSON documents, CBOR binary files and CSV files against CDDL documents, with support for RFC 9165, RFC 9682 and RFC 9741 — [anweiss/cddl](https://github.com/anweiss/cddl); [lib.rs/crates/cddl](https://lib.rs/crates/cddl)
- **CDDL is designed to be composed with ABNF**: RFC 9165 defines `.abnf`/`.abnfb` control operators for embedding ABNF (RFC 5234/7405) in CDDL, with the stated motivation that many IETF protocols define allowed text values in ABNF and without this the grammar "would often have to be translated into a regular expression" — [RFC 9165](https://www.rfc-editor.org/rfc/rfc9165.html)
- **XSD**: I found no source defining XSD coverage criteria (element, attribute, facet, content-model-branch, occurrence-bound coverage). The closest research is Petrova-Antonova, Kuncheva & Ilieva (2015), which compares tools on features including **optional and repeating elements, choice groups, and valid vs invalid data generation** — [SciTePress 2015](https://www.scitepress.org/PublishedPapers/2015/55006/55006.pdf). Commercial tooling (Informatica TDM) exposes only cardinality controls (min/max child records), not coverage criteria — [Informatica TDM XSD data sources](https://docs.informatica.com/data-security-group/test-data-management/10-5/user-guide/projects/data-sources/xsd-data-sources.html)
- **ASN.1 → TTCN historically**: TESTGEN generated TTCN test suites from an extended transition system (ETS) model combined with ASN.1 descriptions of protocol data, explicitly to cover "both the control part and the data part of a protocol" — [UBC library record](https://open.library.ubc.ca/collections/831/items/1.0051975). Ericsson training material lists ASN.1 alongside UML and SDL as formal inputs for automatic test design but calls Computer Aided Test Generation "an open problem" — [BME TTCN-3 course deck](https://wiki.sch.bme.hu/images/0/00/Protokolltechn_TTCN3_2013.pdf)
- **OpenAPI/JSON Schema practitioner recipe** (useful because it states the one-rule-at-a-time discipline concretely): start from a known-valid request and change **one contract rule per test**; `minimum: 1` yields a valid case at 1 and an invalid case at 0; `maxLength: 20` yields 20 valid code points and 21 invalid; do one-constraint mutations first, then pairwise/property-based combinations. It also warns that a validation layer may reject the mutated input before it reaches the code under test — [OneUptime, negative/boundary tests from OpenAPI](https://oneuptime.com/blog/post/2026-08-24-openapi-negative-boundary-tests/markdown)

### Inferences
- The two coverage ladders are isomorphic and both are notation-agnostic: *production coverage over a grammar* ≡ *one choice per category over a field inventory* ≡ *at least one test per ICS item* (see Q3). The tool's existing 29119-4 ladder is a third instance of the same idea, which is why it already produces per-field enumeration; the deficit is in the *inventory it enumerates over*, not the ladder.
- Yield per field is fixable by construction rather than by literature lookup. Berserker's Table 2 is effectively a per-type test-purpose template set: presence (2 purposes per OPTIONAL field: omitted / present), size (2 per SIZE-constrained field: below lower, above upper), enumeration (1 valid per option + 1 unknown option), type confusion (1 per primitive type substitution), ordering (1 per SEQUENCE/CHOICE), cardinality (2 per SEQUENCE OF). Applied to the official suite's observed shape — 455 presence + 257 type/encoding + 97 value-domain + 8 size/boundary over 118 families — the implied human template is roughly 3.9 presence, 2.2 encoding and 0.8 value-domain purposes per family, i.e. a small fixed template per field attribute, which is exactly what a notation-driven enumerator produces.
- Derivation coverage is the wrong criterion for this genre and should be avoided; production/k-path (k=1 or 2) is the matching level, since the official suite is a per-field enumeration rather than an enumeration over whole-message derivations.

### Gaps
- No source reports a **tests-per-field or tests-per-production ratio** for any schema-driven generator. All counts I found are totals for one artefact.
- No XSD/JSON Schema coverage-criteria paper located despite two queries; the area appears to be dominated by tool documentation rather than defined criteria.
- SYNTest's method and yield not retrieved (paywalled IEEE).

## Q3. How practitioners test a certificate or message profile defined as a table of fields with presence and value constraints; tooling that consumes a profile table and emits a test matrix

### Takeaway
There is a mature, standardised answer for the *checklist-to-test-purpose* direction — ISO/IEC 9646's ICS/PICS proforma, with the explicit rule that **every mandatory or optional ICS item must be covered by at least one test purpose** — and mature tooling for the *check a certificate against a profile* direction (pkilint, GSA CPCT). What does **not** appear to exist is a tool that consumes a profile table and emits abstract test purposes or a conformance test matrix; the linters embed the profile in code and the test-purpose derivation remains a documented manual process.

### Cited Findings

**ISO/IEC 9646 ICS/PICS machinery (the genre's own mechanism)**
- "The ICS proforma is a normative part of the reference specification. The supplier of an implementation which is claimed to conform is required to complete a copy of these ICS proforma" — [ETSI TS 103 096-3](https://etsi.org/deliver/etsi_TS/103000_103099/10309603/01.02.01_60/ts_10309603v010201p.pdf)
- The ICS has five documented uses in conformance assessment: description of the IUT for the **static conformance review**; description of IUT capabilities for **test case deselection**; description of the IUT for **test suite parametrization**; reference document for **analysis of results**; and inclusion with the **final test report** — [ETSI TS 103 096-3](https://etsi.org/deliver/etsi_TS/103000_103099/10309603/01.02.01_60/ts_10309603v010201p.pdf)
- ISO/IEC 9646-7:1995 is the part dedicated to Implementation Conformance Statements — [IEC preview of ISO/IEC 9646-7](https://webstore.iec.ch/preview/info_isoiec9646-7%7Bed1.0%7Den.pdf)
- ISO/IEC 9646-5:1994 places the static conformance review at clause 7.2, followed by test selection (7.3) and test parameterization (7.4) — [ANSI preview of ISO/IEC 9646-5](https://webstore.ansi.org/preview-pages/ISO/preview_ISO+IEC+9646-5-1994.pdf)
- ISO/IEC 9646-2 covers abstract test suite production and is "applicable to the production of abstract test cases which check the conformance of an implementation to the relevant **static and/or dynamic** conformance requirements" — i.e. static (presence/profile) requirements are in scope for the abstract test suite, not only behaviour — [ISO/IEC 9646-2:1994 catalogue](https://online.standard.no/en/isoiec-9646-2-1994)
- ISO/IEC 9646-6:1994 specifies requirements for **Profile Test Specifications (PTSs)** for conformance testing of protocol profiles — [SCC record](https://scc-ccn.ca/standardsdb/standards/8108005)
- **ETSI's chain is explicit**: requirements from scattered sources are gathered into a single **requirements catalogue** that "should list all implementation requirements from the various sources and organize them into an appropriate structure"; test purposes are derived from the base standards or that catalogue, give "an informal, easy-to-read self-contained description of each test, concentrating on what is to be tested rather than how", and are organised into a **Test Suite Structure (TSS)**; test cases then "specif[y] the detailed coding of the Test Purposes" in TTCN — [ETSI CTI, Conformance Testing](https://portal.etsi.org/Services/Centre-for-Testing-Interoperability/ETSI-Approach/Conformance)
- **The coverage rule for a field table** is stated as normative guidance in ETSI ETR 266 (August 1996), the Test Purpose style guide: *"Guidance 5: The Test specifier should check that any mandatory or optional item of the ICS is covered by at least one TP."* It adds that coverage checking "is limited to a cross-check of the TP versus the ICS entries" when the method was followed, and is "extremely time-consuming" when the TP-to-ICS relationship is not recorded — [ETSI ETR 266, *Methods for Testing and Specification (MTS); Test Purpose style guide*, August 1996](https://www.etsi.org/deliver/etsi_etr/200_299/266/01_60/etr_266e01p.pdf) (PDF text extracted locally; one retailer lists the report as withdrawn, so check current ETSI status)
- ETR 266's documented TP production process, starting from requirements: (1) identify all conformance requirements of the reference specification; (2) **identify the PICS entry(ies) corresponding to each**; (3) structure requirements into nested homogeneous groups, giving a first TSS; (4) compare against ISO/IEC 9646-2's basic guidance and close gaps; (5) define TPs corresponding to the requirements or requirement sets; (6) feed the TSS tree with them; (7) refine iteratively; (8) **check coverage**. The guide states this is "preferred" over starting from a pre-defined TSS, and that "the TSS structure applicable to a given standard should not be defined a priori, but should be the result of the process of conformance requirements analysis" — [ETSI ETR 266 (Aug 1996)](https://www.etsi.org/deliver/etsi_etr/200_299/266/01_60/etr_266e01p.pdf)
- ETR 266's TP component list is: Identifier (which "should be identified by the same referencing scheme as the Test Suite Structure"), Reference to the requirements ("the subclause of the reference standard specifications in which the conformance requirement is expressed"), Reference to the selection criteria ("should relate to the PICS items and/or the PIXIT details related to the support of the element concerned"), Test summary, Initial conditions, Check(s) to be performed, Verdict criteria, Constraints — [ETSI ETR 266 (Aug 1996)](https://www.etsi.org/deliver/etsi_etr/200_299/266/01_60/etr_266e01p.pdf)
- For protocol standards the ICS is called the **PICS** and its companion the IXIT the **PIXIT**, the latter carrying "specific addresses and timer values needed for testing" — [ETSI CTI, Conformance Testing](https://portal.etsi.org/Services/Centre-for-Testing-Interoperability/ETSI-Approach/Conformance)
- **TPLan** (ETSI ES 202 553) is a structured notation for test purposes with a minimal set of communications-oriented keywords and user-defined extensions; a TP has a header (TP id, Summary, requirement reference, configuration, test case reference) followed by `ensure that { when { ... } then { ... } }` — [ETSI TPLan page](https://portal.etsi.org/CTI/ApproachToTesting/TestLanguages/TPLAN.htm); [ETSI ES 202 553](https://www.etsi.org/deliver/etsi_ES/202500_202599/202553/01.01.01_50/es_202553v010101m.pdf)
- Adoption caveat: ETSI's own STF 476 report on TDL found that "the informal nature of TPLan leads to potential inconsistencies and ambiguities in the specifications, and poor or no tool support", that TPLan "has not been decisively adopted as the notation of choice for the specification of test purposes at ETSI", and that "a variety of 'dialects' have emerged which adopt certain notions from TPLan" — [ETSI STF 476 Task 4 Report](https://docbox.etsi.org/STF/Archive/STF476_MTS_TDL2/Public/STF%20476%20-%20Task%204%20Report.pdf)

**Certificate profile tooling**
- **pkilint** (DigiCert, MIT licence) is built on an **ASN.1 parser**, which lets it check encoding errors; it lints certificates, CRLs and OCSP responses; "its validation logic analyzes every field of an ASN.1 document and decides which sets of tests to run"; its first release implements **more than 145 separate tests** against the CA/Browser Forum S/MIME Baseline Requirements and related standards — [DigiCert blog](https://digicert.com/blog/digicert-releases-automated-testing-tool-for-digital-certificates); [CA/B Forum SMCWG announcement](https://lists.cabforum.org/pipermail/smcwg-public/2023-May/000673.html)
- pkilint exposes its own test matrix: "each linter bundled with pkilint can list its validations using the `validations` sub-command" — [SMCWG thread](https://lists.cabforum.org/pipermail/smcwg-public/2023-May/000678.html)
- The generation side is a **separate** tool: **SMBR-Cert-Factory** "generates test certificates compliant with the certificate profiles defined in the S/MIME BRs" — [DigiCert blog](https://digicert.com/blog/digicert-releases-automated-testing-tool-for-digital-certificates)
- **GSA Certificate Profile Conformance Tool (CPCT)** "analyzes certificates for conformance to a specific Federal PKI profile document version and certificate profile", runs locally under Docker, and in v2.0.1 covered Common SSP v2.2, FPKI/Federal Bridge v2.0, and PIV-I 1.2/1.3 (legacy); it is paired with the Card Conformance Tool for smart cards, both built for remote FPKI Annual Review testing — [GSA test tools page](https://www.idmanagement.gov/implement/announcements/test-tools/); [GSA/cpct-tool releases](https://github.com/GSA/cpct-tool/releases)
- The FPKI certificate profiles themselves are published as profile tables with presence columns — [FPKI/FBCA profiles PDF](https://devicepki.idmanagement.gov/docs/archived/fpki-fbca-profiles-19.pdf)
- I found **no** source confirming pkilint generates conformance test cases; search explicitly returned none, and "fpkilint" could not be confirmed as an existing tool — [search result note](https://www.idmanagement.gov/implement/announcements/test-tools/)

### Inferences
- **ETR 266's TP component list maps almost field-for-field onto the ISO/IEC TS 18013-6 record structure**: Identifier → Test case ID; Reference to the requirements → Reference; Reference to the selection criteria (PICS/PIXIT) → Technology (applicability) and Profile (configuration precondition, present in 595/907 cases); Initial conditions → Preconditions; Test summary → Purpose; Check(s) to be performed → Test scenario; Verdict criteria → Expected results. The two-way split of the ETR 266 selection-criteria field into an applicability tag and a configuration tag is the only real divergence. This identifies the official suite's genre precisely and supplies the generation contract: the tool should emit records with these eight or nine slots, with the Reference slot carrying the clause citation and the selection-criteria slot carrying the ICS/profile condition.
- **The 455 presence/absence checks are a mechanical consequence of ETR 266 Guidance 5 applied to the standard's data-element tables.** A table of fields with a presence column mandatory/optional/conditional *is* an ICS proforma in all but name; "every mandatory or optional item covered by at least one TP" generates one presence purpose per mandatory item and (in practice) a present/absent pair per optional item. This is the single most transferable mechanism found, and it is free of any notation commitment.
- Because the ICS is also the **deselection** mechanism, the applicability tag is not decoration: the human suite's Technology and Profile fields are what let 595 of 907 cases be conditioned. A generator that omits an applicability slot cannot reproduce the genre even if its purposes are right.
- The tooling gap is real and one-directional: the industry has converged on **profile-as-code checkers** (pkilint, CPCT) where the profile table has been hand-transcribed into validation code, plus separate **profile-conformant artefact factories** (SMBR-Cert-Factory). Nobody appears to treat the profile table as data that generates a test matrix. pkilint's `validations` subcommand is the nearest thing to a machine-readable test matrix derived from a profile, but it is an output of hand-written code, not of the table.

### Gaps
- No tool found that consumes a certificate profile table (or CDDL, ASN.1, JSON Schema) and **emits abstract test purposes or a conformance test matrix**. Searched from three directions (pkilint/profile, ASN.1/TTCN, TPLan/ICS). I consider this a genuine negative result rather than a search failure, but it is a negative result from four queries, not an exhaustive survey.
- ISO/IEC 9646-2's actual test-purpose derivation clauses and 9646-5 clause 7.2's static-conformance-review procedure are paywalled; I have only catalogue abstracts and the ETSI restatements.
- ETSI ES 202 553 is marked inactive on one aggregator — [GlobalSpec](https://standards.globalspec.com/std/1095255/es-202-553) — so its current ETSI status should be checked before citing it as live practice.

## Q4. Tools that parse formal blocks out of a standards document automatically, and their limits

### Takeaway
Per-notation extractors exist and are in production use at IETF (ABNF via BAP, YANG via rfcstrip/xym) and in research (ASN.1 from 3GPP Word sources), but every one of them depends on a convention — an explicit code-block marker, or a notation-specific lexical signature — and each documents the same failure mode: without the marker the extractor silently produces the wrong thing. No extractor was found for CDDL, nor for certificate-profile tables.

### Cited Findings
- **IETF Author Tools ABNF service** uses **Bill's ABNF Parser (BAP)** to "extract & parse ABNF syntax" from a text Internet-Draft or RFC given by URL or name. Its documented limits: the output "is a concatenation of all the ABNF fragments in the document, including the appendix. Therefore results may include duplicates and invalid ABNF syntax." — [author-tools.ietf.org/abnf](https://author-tools.ietf.org/abnf)
- That behaviour is actively discussed: a 2024 CBOR WG thread "Exploring ABNF extracts from RFCs" debates it, with Carsten Bormann arguing that a document reference should be kept separate from how the referenced item is used — [IETF CBOR mail archive](https://mailarchive.ietf.org/arch/msg/cbor/BzPmdKJyM7gOlrASb2zkDmmg84g/)
- **rfcstrip** extracts YANG modules from an Internet-Draft or RFC text file (`rfcstrip <file>`), source at github.com/mbj4668/rfcstrip, with output checkable by pyang or yanglint — [IETF OPS wiki, YANG review tools](https://wiki.ietf.org/group/ops/yang-review-tools)
- **rfcstrip's limit is marker-dependence**: a YANG Doctors review of RFC 8407bis notes the filename after the `<CODE BEGINS>` tag is only a SHOULD, and "if there is no such a 'file name', the tool 'rfcstrip' will not extract the correct file" — [datatracker review](https://datatracker.ietf.org/doc/review-ietf-netmod-rfc8407bis-11-yangdoctors-lc-liu-2024-06-17/00/)
- **xym** fetches and extracts YANG modules from IETF RFCs and drafts, from a local text/RFCXML file or a URL, writing `.yang` files, and can parse an RFCXMLv3 source with `--rfcxml` — [PyPI: xym](https://pypi.org/project/xym/); [xym-tool/xym](https://github.com/xym-tool/xym)
- **Berserker's RRC ASN.1 schema extractor** "extracts all RRC message definitions from a 3GPP RRC TS" working from the MS Word source and emitting "the complete RRC ASN.1 schema into a single plain text file"; the authors claim it works "directly from any 3GPP RRC TS for 4G and 5G" and keeps the tool aligned with evolving 3GPP TSes — [arXiv:2107.01912](https://arxiv.org/pdf/2107.01912)
- An independent extractor of the same kind predates it: OpenAirInterface, "ASN.1 extractor from 3GPP specifications", 2020, gitlab.eurecom.fr/oai/ — [arXiv:2107.01912 reference 43](https://arxiv.org/pdf/2107.01912)
- **No CDDL extractor found.** Searching specifically for one returned only CDDL parsers/validators (cddl-rs, a project-specific Go cddltool, the Ruby `cddlc` gem) — [lib.rs/crates/cddl](https://lib.rs/crates/cddl); [anweiss/cddl](https://github.com/anweiss/cddl)
- A related structural aid exists for text RFCs regardless of notation: RFC 8792 line-folding conventions, and CDDL's own formal definition is given in ABNF in RFC 8610 Appendix B, so a CDDL block is itself parseable by an ABNF-derived parser — [RFC 8610](https://www.rfc-editor.org/rfc/rfc8610.html)

### Inferences
- Both production extractors are **marker-driven, not notation-driven**: BAP looks for ABNF-shaped text, rfcstrip looks for `<CODE BEGINS>`. In RFCXML v3 the marker is structural and typed (`<sourcecode type="...">`), which is why xym gained an `--rfcxml` mode. ISO documents have no equivalent typed marker, so a generic dispatcher over ISO PDFs must reconstruct the marker from layout and lexical signatures — which is the step that has no published accuracy figure anywhere I looked.
- The BAP limitation ("may include duplicates and invalid ABNF") is instructive for a generic pipeline: a naive all-blocks concatenation is usable as a *candidate* set but not as a model. The extracted text needs a notation-specific parse as the acceptance test, which is precisely what makes the dispatch generic — detection can be sloppy because the handler's parser is the gate.

### Gaps
- I could not confirm the existence of an IANA/RFC registry of `sourcecode` type values (two queries returned nothing). RFCXML's `<sourcecode type>` attribute is referenced indirectly via xym's `--rfcxml` option, but I have no primary citation for the attribute or a registry of its values.
- No accuracy figure exists for any of these extractors: none of BAP, rfcstrip, xym or Berserker's extractor reports recall against a hand-built ground truth of blocks present in the document.
- Nothing found on extracting **tables** (data-element tables, certificate profile tables) as structured records from standards documents, despite this being the artefact class the official suite enumerates most heavily.

## Q5. How the completeness of an extracted model is measured, and what completeness others have achieved on real standards

### Takeaway
The field has settled on one method — build a **golden/canonical model by hand for a handful of protocols, then report per-element recall against it, broken out by element kind** — plus one behavioural proxy: run the extracted model as a generator and measure what fraction of its outputs a real implementation accepts. Best achieved completeness on real standards: 95–100% for message types and field names, 82–91% for field types and independent constraints, 44% for dependent constraints, and roughly 85% for state transitions only when human annotations are supplied.

### Cited Findings
- **Per-element-kind recall against a hand-built golden model** is ParCleanse's method and gives the best figures on record: message types 100%, field names 95%, field types 91%, independent constraints 82%, dependent constraints 44% — [alphaXiv overview of arXiv:2504.18050](https://www.alphaxiv.org/overview/2504.18050)
- AUTOSPEC uses the same method against hand-written "golden grammars" (e.g. POP3: 295 LoC, 24 message types) and reports message-type recall 92.8%/80.2% (client/server) but constraint recall 16.7% independent / 0.0% dependent — [arXiv:2511.17977](https://arxiv.org/html/2511.17977v1)
- **Behavioural completeness proxy**: AUTOSPEC measures "message acceptance" and "trace acceptance" — the fraction of messages/traces generated from the extracted grammar that real servers accept — averaging 81.5% for messages, with trace acceptance consistently lower (SMTP 57.1% vs message 72.7%) — [arXiv:2511.17977](https://arxiv.org/html/2511.17977v1)
- **Error attribution as a completeness ceiling**: Pacheco et al. classify the residual errors in their gold-annotated FSMs and attribute 67% (TCP) and 96% (DCCP) to information missing from or ambiguous in the document, concluding that "a complete one-to-one mapping to canonical FSMs isn't possible" — [arXiv:2202.09470](https://ar5iv.labs.arxiv.org/html/2202.09470)
- Pacheco et al. also report completeness as raw transition counts (correct / partially correct / incorrect / not found) rather than recall, with ~17 of 20 canonical TCP transitions recovered correctly or partially — [arXiv:2202.09470](https://ar5iv.labs.arxiv.org/html/2202.09470)
- **Benchmark-with-fuzzy-matching**: PSMBench scores against 108 validated states and 297 transitions over 14 protocols using structure-aware semantic fuzzy matching "that reward[s] partially correct graphs", with best state-set F1 0.715 — [PSMBench listing](https://mlanthology.org/neurips/2025/shen2025neurips-psmbench) (secondhand, see Q1 caveat)
- **Coverage-against-the-checklist** is the standards-world measure and is the cheapest: ETR 266 Guidance 5 reduces completeness to "a cross-check of the TP versus the ICS entries", and warns the cross-check becomes "extremely time-consuming" if the TP-to-ICS relationship is not recorded in the TP — [ETSI ETR 266 (Aug 1996)](https://www.etsi.org/deliver/etsi_etr/200_299/266/01_60/etr_266e01p.pdf)
- **Span-level NLP metrics** are the fourth measure in use: SemEval-style strict and exact span scores on the intermediate representation, reported separately from downstream model quality (NeuralCRF: span-strict 68.81, span-exact 86.83) — [arXiv:2202.09470](https://ar5iv.labs.arxiv.org/html/2202.09470)

### Inferences
- The four measures sit at different points and are not interchangeable: span metrics measure *annotation*, per-element recall measures *model*, acceptance rate measures *behaviour*, ICS cross-check measures *suite*. For a generator judged against a human abstract test-purpose suite, the ICS cross-check and per-element recall are the relevant pair; acceptance rate is unavailable pre-implementation, which is a structural advantage of the ICS-style measure for a before-implementation tool.
- The gap between span-exact (86.83) and span-strict (68.81) in Pacheco, and between message recall and constraint recall everywhere, both point the same way: **what is extracted is usually the right span with the wrong label or the wrong attribute**. For a field-inventory target this is good news — the inventory is recoverable at 95%+ — and bad news for the value-domain and conditional-presence attributes, which is where the official suite's 97 value-domain checks live.
- No one measures completeness of a *field inventory extracted from a table*; ParCleanse's 95% field-name recall is the closest proxy and comes from prose plus format diagrams in RFCs, not from tables.

### Gaps
- No completeness figure anywhere for recovering a field inventory from an **ISO** document, or from any document whose primary carrier is a table rather than prose or ASCII art.
- No source reports completeness of an extracted model measured against a **human conformance test suite** (the measurement the project is actually doing). The 13.8% figure has no published peer; I found nothing comparable to cite as a baseline.

## Q6. Which techniques are notation-agnostic, and the general shape of a detect-and-dispatch pipeline

### Takeaway
The coverage ladders and the ICS coverage rule are fully notation-agnostic; only the handlers are not. The pipeline shape that the located work converges on is: **section-level classification with an action label → notation-specific parse as the acceptance gate → normalisation into one typed field/constraint graph → deterministic enumeration over that graph → record emission with a citation back to the source span.** Two of these stages (classification-with-action, trace-back-to-span) are implemented identically in ParCleanse and AUTOSPEC despite different targets, which is the best evidence of genericity.

### Cited Findings

**Notation-agnostic components (each cited above, collected here)**
- Coverage criteria over a structure: terminal / production / derivation coverage, and k-path — defined purely over a grammar's shape, with no notation commitment — [UVA slides](https://cs.virginia.edu/~up3f/cs3250/slides/3250meet29-syntax-grammar.pdf); [CISPA k-path](https://publications.cispa.de/articles/journal_contribution/From_Input_Coverage_to_Code_Coverage_Systematically_Covering_Input_Structure_with_k-Paths/24612432)
- Category-partition: categories → choices → test frames, with constraints pruning; defined over "parameters and environment conditions", not over any notation — [Ostrand & Balcer 1988](https://faculty.cc.gatech.edu/~harrold/6340/cs6340_fall2009/Readings/ostrandCategoryPartition88.pdf)
- One-rule-at-a-time mutation (single-error, then double, then triple), the core of syntax/anti-syntax testing — [UWA CITS5501](https://teaching.csse.uwa.edu.au/units/CITS5501//lectures/lect05c--mutation.pdf)
- ICS coverage: "any mandatory or optional item of the ICS is covered by at least one TP" — applies to any table of items with a presence column — [ETSI ETR 266 (Aug 1996)](https://www.etsi.org/deliver/etsi_etr/200_299/266/01_60/etr_266e01p.pdf)
- The TP record structure itself (identifier tied to the TSS scheme, requirement reference, selection criteria, initial conditions, checks, verdict) — [ETSI ETR 266 (Aug 1996)](https://www.etsi.org/deliver/etsi_etr/200_299/266/01_60/etr_266e01p.pdf)
- Protocol-independent intermediate representation: Pacheco et al.'s XML annotation grammar is explicitly described as "a general-purpose abstraction", and their approach is zero-shot, with "no portions of a test protocol observed during training" — [arXiv:2202.09470](https://ar5iv.labs.arxiv.org/html/2202.09470)

**Dispatch stage as implemented**
- AUTOSPEC's stage 1 is exactly a dispatcher: an LLM labels each RFC section with a **class** (state machine / overview / example / other) and an **action** (extract / copy / summarize), and only "extract" sections proceed. Stage 2 then validates each extracted fragment against a **Pydantic model**, re-prompting once on failure — i.e. the schema parse is the acceptance gate — [arXiv:2511.17977](https://arxiv.org/html/2511.17977v1)
- AUTOSPEC states that "models and protocol targets are pluggable via configuration" — [arXiv:2511.17977](https://arxiv.org/html/2511.17977v1)
- ParCleanse's DocTree plays the same role structurally: extract a format per section, **syntax-check each format**, then merge sub-formats bottom-up along the tree into one format graph — [alphaXiv overview](https://www.alphaxiv.org/overview/2504.18050)
- Both systems keep a span-level pointer back to the document: ParCleanse maps each inconsistency to DocTree sections and then diagnoses bug-vs-hallucination; AUTOSPEC "aligns RFC excerpts" to the FSM skeleton — [alphaXiv overview](https://www.alphaxiv.org/overview/2504.18050); [arXiv:2511.17977](https://arxiv.org/html/2511.17977v1)
- Berserker's two-level design generalises beyond ASN.1 in shape if not in code: mutate the **schema** (type substitution, option extension/reduction/reordering, size-bound change) and separately mutate **values** per type — a split that applies to any typed data definition — [arXiv:2107.01912](https://arxiv.org/pdf/2107.01912)

**Handling externally defined structures (fields defined in a referenced document)**
- CDDL has a standards-track answer in progress: **draft-ietf-cbor-cddl-modules-07** (September 2026) defines `include` and `import` directives, where `import` "includes only those rules from the module that are referenced from the importing module, implicitly or explicitly … including the rules that are referenced from these rules, transitively", with an `as` clause to prefix imported names and avoid collisions, and it is designed for forward compatibility so "a single file can be designed to serve both as valid basic CDDL and as a module with directives" — [draft-ietf-cbor-cddl-modules-07](https://www.ietf.org/archive/id/draft-ietf-cbor-cddl-modules-07.html)
- The draft's worked example is directly the case at hand: a `cddlc` command-line run that **imports the `COSE_Key` definition from RFC 9052** into a small start rule, outputting a flattened CDDL 1.0 specification containing the imported rule and its transitive dependencies; the draft frames `include` as composing one model from parts by one author and `import` as "treating a module as a library" — [draft-ietf-cbor-cddl-modules-07](https://www.ietf.org/archive/id/draft-ietf-cbor-cddl-modules-07.html)
- Status caveat: this is an Internet-Draft, which by its own boilerplate is "inappropriate to use … as reference material or to cite … other than as work in progress" — [draft-ietf-cbor-cddl-modules-07](https://www.ietf.org/archive/id/draft-ietf-cbor-cddl-modules-07.html)
- The equivalent cross-notation bridge is already an RFC: RFC 9165's `.abnf`/`.abnfb` control operators embed ABNF grammars inside CDDL, motivated by the fact that "many IETF protocols define allowed text values in ABNF" — [RFC 9165](https://www.rfc-editor.org/rfc/rfc9165.html)
- For profiles over externally defined structures, pkilint is the production pattern: an ASN.1-parser core implementing RFC 5280-level structure, with a CA/B Forum S/MIME BR overlay of 145+ tests, and "validation logic [that] analyzes every field of an ASN.1 document and decides which sets of tests to run" — [DigiCert blog](https://digicert.com/blog/digicert-releases-automated-testing-tool-for-digital-certificates); [SMCWG announcement](https://lists.cabforum.org/pipermail/smcwg-public/2023-May/000673.html)
- ASN.1's own mechanism for the same problem is `IMPORTS … FROM`, exploited by Berserker's extractor insofar as it emits "the complete RRC ASN.1 schema into a single plain text file" — i.e. flattening, the same strategy as `cddlc` — [arXiv:2107.01912](https://arxiv.org/pdf/2107.01912)

### Inferences
- The pipeline shape that both ParCleanse and AUTOSPEC independently arrived at — classify section, extract to a schema-validated fragment, merge along the document tree, keep the span pointer — is the generic dispatch answer, and it differs from the project's current pipeline in exactly one place: the **classify** step emits a notation label and routes to a parser, rather than emitting a prose requirement. The acceptance gate is the handler's own parser (BAP for ABNF, a CDDL parser, an ASN.1 compiler, a JSON Schema metaschema check), which means detection can be cheap and recall-oriented: a false positive is rejected by the parser, a false negative silently reverts to the existing prose path. That asymmetry is what makes a generic detector safe to add.
- **The right normal form is a typed field/constraint graph, not a grammar.** Four independent pieces of evidence: ParCleanse's format graph (DAG of fields, types, constraints) achieves 5× AUTOSPEC's constraint recall; the official suite's own shape (presence / type-encoding / value-domain / size per field) is a field-attribute enumeration; Berserker's Table 2 is keyed on type-plus-qualifier, not on productions; and every notation in scope (CDDL, ASN.1, JSON Schema, XSD, Protobuf, a certificate profile table, a data-element table) projects onto field-name + presence + type/encoding + value-domain + size + relation, which is also precisely the "object with attributes" schema the tool's second LLM pass already targets. So the dispatch can be additive: new handlers populate the existing object/attribute store deterministically, and the existing 29119-4 coverage-item enumerator is unchanged.
- **External structures are solved by flattening, and the flatteners exist.** `cddlc` with `import` resolves a COSE structure from RFC 9052 transitively into one CDDL file; an ASN.1 compiler resolves `IMPORTS`; pkilint resolves RFC 5280 structure then overlays the profile. All three produce the full field inventory of an externally defined structure, which is what a family like `Common_COSESign1_01..NN` enumerates. This means the externally-defined-field problem is a *dependency-resolution* problem with existing tooling, not an extraction problem — provided the referencing standard's citation of the external document can be turned into a module reference.
- The genre's reuse-by-reference idiom ("perform all Common_X test cases specified in Appendix 1, clause N", 27 cases in the official suite) is the test-suite-level mirror of `import`: a structure defined once and enumerated once, referenced thereafter. A generator that resolves imports by flattening will *over*-generate relative to the human suite unless it also models this reuse, by emitting one family per structure plus reference stubs per usage site.

### Gaps
- I found no published pipeline that performs notation detection and dispatch over multiple notations in one document. Every located system handles exactly one target notation. The dispatch design above is therefore an inference from two single-notation pipelines plus the IETF extractor ecosystem, not a reported architecture.
- No tool found that maps a standard's prose citation of an external specification to a resolvable module reference automatically; `cddlc` import and ASN.1 IMPORTS both require the reference to be written in the notation already.
- Nothing located on Protobuf-driven conformance test or test-purpose generation; the question's Protobuf leg is unanswered.
