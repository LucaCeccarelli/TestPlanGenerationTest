# Systematic test-design methods that enumerate a test suite from a model, and the coverage criteria that say when the enumeration is complete

Scope note for the report-writer: everything below is method-generic (applies to RFCs, OpenID specs, ISO standards, ETSI/3GPP deliverables). The mDL measurement (907 cases / 687 clause-citing / 118 families / 7.7 per family / 13.8 % covered by 3257 generated coverage items) is used only as the yardstick. Where the standard text itself is paywalled beyond the free preview, I say so rather than paraphrasing from memory.

Two findings dominate and should frame the report:

1. **ISO/IEC/IEEE 29119-4:2021 names twelve specification-based techniques, not two.** The tool's ladder is effectively `equivalence partitioning + boundary value analysis` only. Syntax testing, combinatorial test design, decision table testing, cause-effect graphing, state transition testing, scenario testing, requirements-based testing, classification tree method, random testing and metamorphic testing are all separate normative clauses with their own coverage-measurement clauses. The verified clause list is below.
2. **The official suite is an ISO/IEC 9646-2 / ITU-T X.291 "Test Suite Structure and Test Purposes" artefact, not a test-case artefact.** That genre has a documented production process, a documented field structure, a documented coverage clause, a documented reuse mechanism (generic test cases, grouping, inclusion) and a documented granularity rule (one requirement per test purpose). Generating into that genre is a different target than generating "a test case per coverage item".

## Q1. Category-partition (Ostrand & Balcer 1988) and classification-tree (Grochtmann & Grimm 1993): decomposition, test-frame counts, constraint mechanisms, tooling

### Takeaway
Both methods decompose a specification into *orthogonal aspects × disjoint value classes* and then take a constrained product; the category-partition constraint set (`[property]`, `[if]`, `[error]`, `[single]`) is a published, mechanical pruning ladder that in the canonical worked example cuts 1944 frames → 678 → 125, i.e. a ~15.6× reduction, and the classification-tree method is the same idea with a tree, a combination table, Boolean dependency rules, and 30 years of tooling (CTE → CTE XL → CTE XL Professional → TESTONA → CTE 4).

### Cited Findings

**Category-partition method (CPM)**
- Origin: T. J. Ostrand and M. J. Balcer, "The category-partition method for specifying and generating functional tests", *Communications of the ACM* 31(6), June 1988, pp. 676–686 — [reading copy at Georgia Tech](https://faculty.cc.gatech.edu/~harrold/6340/cs6340_fall2009/Readings/ostrandCategoryPartition88.pdf) (NB: that scan has no text layer; I could not extract quotes directly from it, so the mechanics below are cited from course material that reproduces the original worked example).
- Workflow: the engineer analyses the specification, writes formal *test specifications* in TSL, and a *generator tool* produces *test frames*, from which test scripts are written — [SFU CMPT course notes](https://coursys.sfu.ca/2023sp-cmpt-276-d2/pages/CategoryPartition)
- Decomposition is two-level and explicitly includes the environment: **parameter categories** and **environment categories**. In the canonical `FIND <pattern> <file>` example the parameter categories are pattern size, quoting, embedded blanks, embedded quotes, filename validity; the environment categories are number of occurrences of the pattern in the file and number of occurrences on the target line — [SFU](https://coursys.sfu.ca/2023sp-cmpt-276-d2/pages/CategoryPartition)
- Each category is partitioned into **choices** — "cases expected to be handled differently or that are error-prone boundaries". A **test frame** is one combination with exactly one choice from every category; frame generation is fully automatable and each frame becomes a work item for a tester to write a test case — [SFU](https://coursys.sfu.ca/2023sp-cmpt-276-d2/pages/CategoryPartition)
- **Unconstrained count** for FIND: 4 × 3 × 3 × 3 × 3 × 3 × 2 = **1944 test frames** — [SFU](https://coursys.sfu.ca/2023sp-cmpt-276-d2/pages/CategoryPartition)
- Constraint mechanism 1 — **properties and selector expressions**: `[property X]` asserts a choice has property X; `[if X]` makes a choice applicable only when X holds; compound selectors such as `[if NonEmpty and Quoted]` are legal. Worked annotations in FIND: empty pattern `[property Empty]`; single/many/over-long patterns `[property NonEmpty]`; quoted pattern `[property Quoted]`; unquoted or improperly quoted `[if NonEmpty]`; one/several embedded blanks `[if NonEmpty and Quoted]`; occurrence counts `[if NonEmpty] [property Match]`; occurrences-on-target-line `[if Match]`. **Result: 1944 → 678 frames** — [SFU](https://coursys.sfu.ca/2023sp-cmpt-276-d2/pages/CategoryPartition)
- Constraint mechanism 2 — **`[error]`**: marks an invalid choice that needs only limited testing (in FIND: pattern longer than any line, improper quoting, non-existent file, omitted filename). Constraint mechanism 3 — **`[single]`**: marks a choice needing only one test case (in FIND: zero occurrences in file, more than one occurrence on a line). **Result: 678 → 125 frames** — [SFU](https://coursys.sfu.ca/2023sp-cmpt-276-d2/pages/CategoryPartition)
- Scaling statement: 20 categories × 4 choices each = 4²⁰ ≈ 10¹² combinations, i.e. combinatorial explosion; all-pairs over the same model is 80 × 76 / 2 = 3040 pairs, and excluding error choices ("all-pairs valid case testing") 60 × 57 / 2 + 20 = 1730 pairs, with each frame covering up to 20 × 19 / 2 = 190 pairs — [SFU](https://coursys.sfu.ca/2023sp-cmpt-276-d2/pages/CategoryPartition)
- Formalisation of the constraint layer: Chen, Poon & Tse, "A Choice Relation Framework for Supporting Category-Partition Test Case Generation" (IEEE TSE 2003) model constraints "in terms of relations among choices and combinations of choices" and add tester-supplied *resource constraints* so generated frames stay inside a budget — [HKU TR-2003-01](https://ai.hku.hk/research/techreps/document/TR-2003-01.pdf)

**Classification-tree method (CTM)**
- Origin and genealogy: developed by Grimm and Grochtmann in 1993 (Grochtmann & Grimm, *Software Testing, Verification & Reliability*, 1993); it is an extension of the category-partition method and is black-box, applicable to hardware, software, embedded systems and UIs — [Wikipedia, Classification Tree Method](https://en.wikipedia.org/wiki/Classification_Tree_Method) (secondary but well-referenced); the CPM-extension reading is corroborated by [a course summary](https://yrkan.com/course/module-03-test-design/classification-tree-method/)
- Decomposition: **classifications** are the test-relevant aspects — and critically these may be *inputs, outputs, environment states or preconditions* — each partitioned into disjoint **classes**; classifications can be grouped into **compositions**; class selection follows equivalence partitioning for abstract cases and boundary-value analysis for concrete ones — [Wikipedia](https://en.wikipedia.org/wiki/Classification_Tree_Method)
- Combination step: a test case picks exactly one class from every classification. Counting rule: **maximum = Cartesian product of all classes; minimum = number of classes in the classification with the most classes.** Worked example (database system): User Privilege (2) × Operation (3) × Access Method (5, with Web Browser refined by Brand (3)) = **30 possible test cases, minimum 5** for full access-method coverage — [Wikipedia](https://en.wikipedia.org/wiki/Classification_Tree_Method)
- Constraints: the tree's refinement mechanism *cannot* express constraints between classes of different classifications; Lehmann & Wegener introduced **Boolean dependency rules** in CTE XL (EuroSTAR 2000) to do so, and later work added numerical constraints (formulas over classifications) — [Wikipedia](https://en.wikipedia.org/wiki/Classification_Tree_Method)
- Documented extensions that matter for a protocol/standards setting: test *sequences* (classifications treated as state machines to generate ordered sequences); embedded-system extensions for timing, signal transitions and event/state distinction (Conrad & Krupp); prioritised generation with weights per class for occurrence probability, error probability or risk — [Wikipedia](https://en.wikipedia.org/wiki/Classification_Tree_Method)
- Tooling lineage with dates: **CTE 1** (1993, Daimler-Benz, Pascal/Unix); **CTE 2** (C/win32, licensed to Razorcat 1997/1998, embedded in TESSY); **CTE XL** (2000, Lehmann & Wegener, Java, adds dependency rules; acquired by Berner & Mattner 2008); **CTE XL Professional** (2010, Eclipse-based rewrite); **TESTONA** (2014 rebrand, free light edition); **CTE 4** (2018, Razorcat Eclipse plug-in for TESSY) — [Wikipedia](https://en.wikipedia.org/wiki/Classification_Tree_Method)
- Razorcat's product description: "The Classification Tree Editor (CTE) is a graphical editor which by means of the Classification Tree Method is used to transform a (functional) specification into a set of test cases" — [Razorcat product listing](https://testmation.etesters.com/product/D7FF18FF-C09F-44C4-770F-7C7A6EC5DC58/classification-tree-editor/)
- Documented limitations: trees become large without decomposition; new users include too many irrelevant aspects; **"No algorithm guides the selection of aspects"** — [Wikipedia](https://en.wikipedia.org/wiki/Classification_Tree_Method)
- Generation in the tool uses combinatorial methods such as all-pairs — [Wikipedia](https://en.wikipedia.org/wiki/Classification_Tree_Method)
- CTM is normative in 29119-4:2021 as clause 5.2.2, with its own coverage clause 6.2.2 — [ISO/IEC/IEEE 29119-4:2021 preview TOC](https://assets.vde-verlag.de/iec-normen/preview-pdf/info_isoiecieee29119-4%7Bed2.0%7Den.pdf)

### Inferences
- **The classification-tree reading of the official suite is directly supported by the method's own definition.** Because CTM explicitly admits *preconditions and environment states* as classifications (not just input parameters), a tree whose classifications are `{object, check type, Technology tag, Profile}` is a legitimate CTM model, not a stretch. The suite's shape (object × check × applicability, with templated preconditions) is exactly a CTM combination table with the applicability tags as classifications and dependency rules suppressing impossible pairs.
- **Counting that tree for the measured suite**: with 118 families as the object axis, a check axis of ~6 families (presence/absence, type-or-encoding, value-domain, behaviour/flow, size/boundary, composite reference) and an applicability axis, the Cartesian maximum is in the tens of thousands, while the CTM *minimum* rule (size of the largest classification) is 118. The human suite sits at 907 — i.e. roughly 7.7× the CTM minimum, which is precisely the "7.7 cases per family" figure. That is consistent with the authors covering each object against several checks but **not** taking the object × check cross product, and is the quantitative signature of a constrained (not exhaustive) combination table.
- **The tool's 3257 → 13.8 % mismatch is the category-partition failure mode in reverse.** CPM's `[error]`/`[single]`/`[if]` ladder exists to shrink an over-large product; the measured generator has no such ladder and no applicability classification, so it produces a large product over the *wrong* axes (checks it invented) while omitting whole classifications the humans used (Technology, Profile, behaviour/flow). Adding the CPM constraint vocabulary alone would shrink the output; adding the missing classifications is what would raise coverage.
- CPM's `[error]` annotation is the published answer to the invalid-case question in Q6: invalid choices are *marked*, deliberately not crossed with everything else, and get one test each. The measured generator's `encoding invalid` / `value invalid` / `boundary outside` rungs are `[error]` choices that have been crossed with everything, which is why the item count inflates without coverage gain.

### Gaps
- I could not extract the original 1988 paper's own wording for the TSL grammar or its exact per-step counts (the Georgia Tech scan is image-only, no text layer; WebFetch returned binary). The 1944 / 678 / 125 figures and the annotation syntax come from course material that reproduces the paper's FIND example, not from the paper itself. The report should cite them as "the canonical FIND example as reproduced in [SFU course notes]" or verify against the ACM original.
- No source found for CTE XL Professional / TESTONA's exact set of combination algorithms (pairwise, t-wise, minimal) or its constraint-rule language; Razorcat/TESTONA vendor documentation was not retrievable. Treat "CTE XL Professional supports pairwise" as unverified.
- No published count of how many test frames CTM yields for a real protocol or data-model standard. The database example (30 frames) is a toy.

## Q2. Combinatorial interaction testing over applicability conditions (Technology tags, Profiles, optional features): reduction, fault detection, tools

### Takeaway
t-way covering arrays are the published mechanism for deciding *which combinations of applicability conditions deserve a test*; the empirical interaction rule (67 % of failures from one parameter, 93 % from 2-way, 98 % from 3-way in one studied application, reaching 100 % at 4–6 way) justifies stopping at small t, and NIST reports 20×–700× test-set reduction versus exhaustive at equal fault detection — but NIST also warns pairwise alone "may miss 10 % to 40 % or more of system bugs".

### Cited Findings
- **The interaction rule (verbatim)**: "Most failures are induced by single factor faults or by the joint combinatorial effect (interaction) of two factors, with progressively fewer failures induced by interactions between three or more factors." — [NIST SP 800-142, *Practical Combinatorial Testing*](https://nvlpubs.nist.gov/nistpubs/Legacy/SP/nistspecialpublication800-142.pdf) (text extracted locally from the PDF)
- **Per-level empirical figures**: "for example, 67 % of the failures were triggered by only a single parameter value, 93 % by 2-way combinations, and 98 % by 3-way combinations. The detection rate curves for the other applications studied are similar, reaching 100 % detection with 4 to 6-way interactions. Studies by other researchers have been consistent with these [results]" — [NIST SP 800-142](https://nvlpubs.nist.gov/nistpubs/Legacy/SP/nistspecialpublication800-142.pdf)
- **Pairwise is not enough**: "pairwise testing may miss 10 % to 40 % or more of system bugs, and is thus not sufficient" — [NIST SP 800-142](https://nvlpubs.nist.gov/nistpubs/Legacy/SP/nistspecialpublication800-142.pdf). A Kuhn presentation puts the same point as pairwise finding "about 50 % to 90 % of flaws" — [reported via NIST/academic tutorial material](https://www.sba-research.org/wp-content/uploads/2019/04/105min-cst-tutorial-ver4.pdf) (secondary; the 10–40 % figure from SP 800-142 is the citable one)
- **Covering-array size, small model** (10 binary variables): t=2 → 10 tests (14 % of exhaustive); t=3 → 18 (25 %); t=4 → 36 (50 %); t=5 → 72 (100 %) — Table 3, [NIST SP 800-142](https://nvlpubs.nist.gov/nistpubs/Legacy/SP/nistspecialpublication800-142.pdf)
- **Covering-array size, realistic model** (Android configuration example): t=2 → 29 tests (0.02 % of exhaustive); t=3 → 137 (0.08 %); t=4 → 625 (0.4 %); t=5 → 2532 (1.5 %); t=6 → 9168 (5.3 %) — Table 5, [NIST SP 800-142](https://nvlpubs.nist.gov/nistpubs/Legacy/SP/nistspecialpublication800-142.pdf)
- **Reduction claim**: "Multiple studies show fault detection equal to exhaustive testing with a 20X to 700X reduction in test set size" — [NIST ACTS project page](https://csrc.nist.gov/projects/automated-combinatorial-testing-for-software)
- **Constraints are first-class**: SP 800-142 §3.3.1 "Invalid Combinations and Constraints" states the common situation that "some combinations cannot be tested because they don't exist for the systems under test" and warns "we cannot simply delete tests with these untestable [combinations]" — [NIST SP 800-142](https://nvlpubs.nist.gov/nistpubs/Legacy/SP/nistspecialpublication800-142.pdf). This is the applicability-condition problem exactly.
- **Random testing is not a substitute for a covering array**: "although pure random testing will generally cover a high percentage of t-way combinations, 100 % coverage of combinations requires a random test set much larger than a covering array" — [NIST SP 800-142](https://nvlpubs.nist.gov/nistpubs/Legacy/SP/nistspecialpublication800-142.pdf)
- **Sequence-covering arrays** exist for ordering/flow coverage (SP 800-142 clause "Sequence-Covering Arrays", with sub-clauses on constructing and using them) — [NIST SP 800-142 TOC](https://nvlpubs.nist.gov/nistpubs/Legacy/SP/nistspecialpublication800-142.pdf). Relevant to the 44 behaviour/protocol-flow checks.
- **Tooling — ACTS**: developed by NIST with the University of Texas at Arlington; generates plans covering 2- to 6-way interactions; first released 2008; public domain, no licence, redistributable including in commercial products; ACTS 3.3 is the current covering-array generator; >4,500 corporate and university users; obtained by emailing NIST; the IPOG algorithm is described as more efficient than other known algorithms; won ICST 2023 Most Influential Paper (Practical) — [NIST ACTS project page](https://csrc.nist.gov/projects/automated-combinatorial-testing-for-software); the 2008/465-organisation figures are from the earlier NIST release — [NIST news](https://www.nist.gov/node/565591)
- **Scale illustration from NIST**: for a product with 34 on/off switches, all 3-way interactions need 33 tests and all 6-way need 522, instead of 17 billion — [NIST news coverage](https://www.nist.gov/node/565591)
- **Combinatorial testing applied to ACTS itself** (Borazjany, Lei, Kacker, Kuhn, ICST 2012, pp. 591–600) found combinatorial testing "effective in terms of achieving high code coverage and fault detection", and that "input space modeling can be a significant undertaking, and needs to be carefully managed" — [NIST CSRC](https://csrc.nist.gov/pubs/conference/2012/04/21/combinatorial-testing-of-acts-a-case-study/final)
- **Source paper for the interaction rule**: Kuhn, Wallace & Gallo, "Software Fault Interactions and Implications for Software Testing", *IEEE TSE* 30(6), June 2004, pp. 418–421, DOI 10.1109/TSE.2004.24. In the medical-device data "the most complex failure reported required 4-way interaction to trigger"; Kuhn: "so far we have not seen a failure involving more than 6 parameters" — [LogiGear interview with D. R. Kuhn](https://magazine.logigear.com/software-testing-tools/an-interview-with-computer-scientist-d-richard-kuhn-about-applications-development-of-combinatorial-research/); [NIST presentation](https://www.nasa.gov/sites/default/files/1-4b-ivv2012kuhn.pdf)
- **29119-4:2021 makes this normative**: clause 5.2.5 "Combinatorial test design techniques" with coverage clause 6.2.5; the standard's Terms clause defines **"base choice / base value — input parameter value used in 'base choice testing' that is normally selected based on being a representative or typical value for the parameter"**, confirming base-choice is one of the standard's combinatorial sub-techniques — [29119-4:2021 preview](https://assets.vde-verlag.de/iec-normen/preview-pdf/info_isoiecieee29119-4%7Bed2.0%7Den.pdf)
- **Cheap combinatorial criteria and their counts** (Ammann & Offutt, *Introduction to Software Testing*, ch. 6 input-space partitioning): **Base Choice Coverage** = one base block per characteristic, a base test using all base blocks, then each later test holds all base choices fixed but one, which takes each non-base value; test count = **1 + Σ(Bᵢ − 1)** over characteristics (worked example: 3 parameters × 4 blocks = 1 + 3 + 3 + 3 tests). **Each Choice Coverage** is "simple, but very few tests". **Multiple Base Choice Coverage** allows several base blocks per characteristic. The base test must be *feasible*, i.e. its base choices must be mutually compatible — [GMU lecture on Ammann & Offutt ch. 6.2](https://cs.gmu.edu/~johnsonb/fall23/lectures/Lecture_17_ISP(6.2).pdf); [UVa CS3250 ISP criteria slides](https://cs.virginia.edu/~up3f/cs3250/slides/3250meet14-ISPcriteria.pdf); [textbook contents](https://www.albany.edu/faculty/offutt/softwaretest/contents.html)
- Ammann & Offutt's five-step method: identify testable functions; find inputs and characteristics; model the input domain; **apply a test criterion to choose block combinations**; refine combinations into concrete inputs — [GMU lecture](https://cs.gmu.edu/~johnsonb/fall23/lectures/Lecture_17_ISP(6.2).pdf)
- A timed variant (Timed Base Choice Coverage) for industrial control software reported better code coverage and mutation scores than standard base-choice tests — [MDH publication 4656](https://www.es.mdh.se/publications/4656-Using_Timed_Base_Choice_Coverage_Criterion_for_Testing_Industrial_Control_Software)

### Inferences
- **Base Choice Coverage is the criterion that explains the measured suite's economics.** For a model `object × check × Technology × Profile`, BCC's count `1 + Σ(Bᵢ − 1)` is linear in the number of blocks, not multiplicative — it produces "one nominal case plus one variation per deviating value". A suite of 907 cases over 118 families at 7.7 cases/family is far closer to a per-family base-choice fan-out than to any cross product. The measured generator's 3257 items are closer to All-Combinations over its (wrong) check axis. Switching the combination criterion from implicit all-combinations to base-choice-over-the-right-classifications is the single highest-leverage change the literature supports.
- **For applicability conditions specifically, pairwise over (Technology × Profile × optional-feature) is the published answer to "which combinations deserve a test".** The Android table (29 tests for t=2 over a realistic configuration space vs 0.02 % of exhaustive) is the right order-of-magnitude analogue for a Technology/Profile space. But SP 800-142's own warning (pairwise misses 10–40 %) and the constraints clause mean the honest recommendation is: **t=2 over applicability tags, with constraints encoding mutually exclusive tags, and t=3 for safety- or security-relevant subsets.**
- Conformance suites in practice do *not* take the cross product of applicability tags: ISO/IEC 9646 solves this by *selection* rather than *combination* — the ICS/PICS answers select the applicable subset of a fixed suite (see Q4). So there are two distinct published mechanisms, and they compose: covering arrays decide which *tag combinations* get a test purpose; the ICS decides which test purposes *run* for a given implementation. A generator needs both, and the measured suite's `Technology` + `Profile` fields are the ICS-selection mechanism, not a combination mechanism.

### Gaps
- I could not extract the per-system cumulative curves (medical devices / browser / HTTP server / NASA database / network security) at each of 1–6 way from the primary Kuhn sources; the PDFs returned binary and SP 800-142 gives only the one illustrative 67/93/98 % triple plus "reaching 100 % detection with 4 to 6-way". The report should either cite the 67/93/98 figure as the single example SP 800-142 gives, or obtain IEEE TSE 30(6) for the full table.
- No study found that applies covering arrays specifically to *conformance-suite applicability predicates* (technology tags / profiles / ICS items). This looks like a genuine gap in the literature, and it is worth saying so in the report.
- PICT and CAgen: not covered by any source I retrieved. ACTS is the only tool I can cite with primary documentation. Do not assert PICT/CAgen capabilities without a further search.

## Q3. ISO/IEC/IEEE 29119-4 in detail: what techniques it defines, what coverage items each prescribes, what coverage measures it defines

### Takeaway
The verified clause list for the 2021 second edition contains **twelve specification-based, seven structure-based and one experience-based technique, each paired one-to-one with a coverage-measurement clause**; the standard's own framing is `create test model (TD1) → identify test coverage items (TD2) → derive test cases (TD3)`, with "a single test model will typically be the basis for several test coverage items" — which is exactly the architecture of the tool under measurement, but instantiated for only two of the twenty techniques.

### Cited Findings
All of the following is extracted from the official free preview of the standard (title/contents/foreword/introduction/scope pages) — [ISO/IEC/IEEE 29119-4:2021 preview PDF, VDE Verlag](https://assets.vde-verlag.de/iec-normen/preview-pdf/info_isoiecieee29119-4%7Bed2.0%7Den.pdf). Edition: **second edition, 2021-10**, which "cancels and replaces the first edition (ISO/IEC/IEEE 29119-4:2015), which has been technically revised".

**Scope (verbatim)**: "This document defines test design techniques that can be used during the test design and implementation process that is defined in ISO/IEC/IEEE 29119-2. Each technique follows the test design and implementation process that is defined in ISO/IEC/IEEE 29119-2 and shown in Figure 1."

**The method architecture (verbatim, Introduction)**: the standard gives detailed guidance per technique on exactly three activities — "create test model (TD1); identify test coverage items (TD2); derive test cases (TD3)". Definitions given there:
- "A **test model** represents testable aspects of a test item, such as a function, transaction, feature, quality attribute, or structural element identified as a basis for testing. **The test model reflects the required test completion criterion in the test strategy.**"
- "**Test coverage items** are attributes of the test model that can be covered during testing. **A single test model will typically be the basis for several test coverage items.**"
- "A **test case** is a set of preconditions, inputs (including actions, where applicable), and expected results, developed to determine whether or not the covered part of the test item has been implemented correctly."
- TD4 (create test procedures) is deliberately excluded "because the process is the same for all techniques".

### Inferences
- **The tool implements TD1→TD2→TD3 faithfully but with one technique.** Its twelve-rung ladder (presence, absence, encoding valid/invalid, value valid/invalid, boundary min/max/outside, consistency, condition true/false) is a hand-rolled fusion of 5.2.1 + 5.2.3 plus a thin slice of 5.2.6. It has **no** syntax-testing stage (which is the technique the 257 encoding checks belong to), **no** state-transition or scenario stage (the 44 behaviour checks), and **no** combinatorial stage (the applicability gating). On the measured breakdown, 257 + 44 = 301 of 687 clause-citing tests, i.e. **~44 % of the official suite, fall under techniques the tool does not implement at all.** That alone bounds what the current ladder can reach and is the clearest arithmetic explanation of 13.8 %.
- The standard's own statement that "the test model reflects the required test completion criterion in the test strategy" means **29119-4 does not supply a completeness criterion by itself** — completeness is relative to a declared completion criterion. A generator claiming systematic completeness must therefore declare, per technique, which coverage measure from clause 6 it targets (e.g. "100 % equivalence partition coverage, 100 % syntax-testing coverage over the declared BNF, pairwise applicability coverage, all-transitions state coverage").
- 29119-4 deliberately does **not** define model-based testing or test-case documentation; those live in 29119-1 and 29119-3. So a tool that generates 29119-3 documents from a 29119-4 ladder is architecturally correct, and the missing piece is not in Part 4 at all — it is the *test suite structure* layer, which 29119-4 explicitly disclaims and which ISO/IEC 9646-2 supplies (Q4).

### Gaps
- **The actual coverage-item definitions and coverage formulae per technique are paywalled.** The free preview ends at clause 3.3. I can cite the clause *names* and the architecture with confidence; I cannot cite, for instance, what 29119-4 says a "syntax testing coverage item" is, or whether its combinatorial coverage measure is expressed as t-wise. iso.org and the ANSI/BSI previews both returned HTTP 403. The report must either buy the standard or mark those details as unverified. This is the single most important remaining gap in the whole assignment.
- Annex F ("Test design technique effectiveness") would be the authoritative source for "expected test counts per model element" and for which techniques are empirically strongest; it is behind the paywall and I found no secondary summary of it.

## Q4. The genre: ISO/IEC 9646-2 / ITU-T X.291 Test Suite Structure and Test Purposes — what the tradition prescribes, including its coverage clause and its reuse mechanism

### Takeaway
The official suite's field structure, applicability tags, family identifiers and `perform all Common_X` references are all named constructs in a 30-year-old normative framework: ITU-T X.291 clause 10 ("Test Suite Structure and Test Purposes") has sub-clauses for the TSS, the TPs, **coverage**, and a compliance clause, and clause 11 defines **generic test suites** — the published mechanism for a suite of reusable, parameterisable test cases instantiated per technology.

### Cited Findings
- **The production process is normative and staged**: X.291 clause 8 is "Abstract Test Suite production process leading to conformance testing standards"; clause 9 "Conformance requirements and PICS proforma"; clause 10 "Test Suite Structure and Test Purposes" with **10.1 Basic requirements, 10.2 Specification of the test suite structure, 10.3 Specification of the test purposes, 10.4 Coverage, 10.5 TSS&TP compliance clause**; clause 11 "Specification of generic test suites"; clause 13 "Specification of ATSs" (13.1 general, 13.2 test cases, 13.3 ATS conformance clause, **13.4 Consistency with protocol**); clause 16 "ATS maintenance"; **Annex D "Guidance on generic test cases"** — [ITU-T X.291 table of contents](https://itu.int/dms_pubrec/itu-t/rec/x/T-REC-X.291-199201-S!!TOC-HTM-E.htm) (X.291 is the ITU-T twin of ISO/IEC 9646-2)
- X.291's title is "OSI Conformance Testing Methodology and Framework for Protocol Recommendations"; it also carries **clause 7 "Requirements on PICS proformas"** and **Annex A "Requirements and guidance for a PICS proforma"**, plus **Annex B "Guidance for protocol specifiers to facilitate conformance testing"** and **Annex C "Incomplete static conformance requirements"** — [ITU-T X.291 TOC](https://itu.int/dms_pubrec/itu-t/rec/x/T-REC-X.291-199201-S!!TOC-HTM-E.htm)
- **Purpose of the framework**: it "describes a methodology for testing implementations of Open System Interconnection (OSI) specifications" and "is widely used by protocol and profile specifiers to help them specify their conformance requirements unambiguously and to provide proformas for suppliers to fill in" — [ISO/IEC 9646 catalogue/overview material](https://itu.int/dms_pubrec/itu-t/rec/x/T-REC-X.290-198811-S!!TOC-HTM-E.htm)
- **PICS vs PIXIT**: the PICS is the supplier's declaration of which options of the base standard were implemented; the PIXIT "contains data and test controls that are necessary for the execution of a dynamic test" — [BME SmartComLab conformance-test course page](https://smartcomlab.tmit.bme.hu/alpha/meresek/ttm18a1_eng.htm)
- **Abstract test suite definition**: the ATS "provides a common approach to specifying conformance test suites at a level that is independent of the means of executing those test suites"; TTCN is the recommended notation; ISO/IEC 9646-2 is titled "Abstract Test Suite specification" — [BME course page](https://smartcomlab.tmit.bme.hu/alpha/meresek/ttm18a1_eng.htm); [Schulz, Wiles & Randall, TPLan, TestCom/FATES 2007, refs 7–8](https://dl.ifip.org/index.html/db/conf/pts/testcom2007/SchulzWR07.pdf)
- **Conformance test categories in the tradition** (the standard way test groups are organised): Basic Interconnection Tests (BITs), capability tests, behaviour tests, conformance resolution tests — [BS EN 29646-1:1992 contents](https://infostore.saiglobal.com/en-gb/standards/bs-en-29646-1-1992-259292_saig_bsi_bsi_600732/)
- **ETSI's five-step pipeline, with the means of specification and the question each step answers** (Table 1 of the TPLan paper, verbatim):
  | Step | Means of specification | Question answered |
  |---|---|---|
  | Requirement (RQ) identification | Text, Tables | Which requirements are to be tested? |
  | Test Purpose (TP) specification | Text, Tables, TPLan | What is to be tested? |
  | Test Description (TD) | Text, Tables, MSCs, etc | How is it to be tested? (informally) |
  | Test Case (TC) specification | TTCN-3, C, Java, Perl, Python, MSC, etc | How is it to be tested? (executable) |
  | Test validation | – | Is test implemented correctly? |
  "For more than 15 years ETSI has applied the methodology prescribed by [ISO/IEC 9646-1, 9646-2] where the development of a complete test specification is broken down into five discrete steps… These steps can be understood as different levels of abstraction that bridge the large intellectual gap between a base specification and the final executable test suite." — [Schulz, Wiles & Randall, "TPLan — A Notation for Expressing Test Purposes", TestCom/FATES 2007, LNCS 4581](https://dl.ifip.org/index.html/db/conf/pts/testcom2007/SchulzWR07.pdf)
- **ETSI's own component definitions**: a Requirements Catalogue "should list all implementation requirements from the various sources"; the ICS is "a checklist of the capabilities defined in the standard", and once completed shows which features and options an implementation supports and **"can guide test selection"**; TPs are "informal, readable descriptions of each test" focused on what to verify rather than how, derived from the base standards or the Requirements Catalogue; the TSS organises TPs "into a logical hierarchy by criteria such as basic interconnection, error handling, or functionality"; the ATS is "the complete set of test cases", each test case being "the detailed coding of one or more TPs in TTCN" — [ETSI CTI, Conformance Testing](https://portal.etsi.org/CTI/ApproachToTesting/Conformance.htm)
- **Traceability is the coverage mechanism**: "Test purposes are derived from the requirements stated in one or more base specifications that define the implementation. **This direct relationship to the requirements makes it possible to make an early assessment of test coverage of the specification and to determine the inter-dependencies between different requirements.**" — [TPLan paper](https://dl.ifip.org/index.html/db/conf/pts/testcom2007/SchulzWR07.pdf)
- **Not every requirement yields a test purpose**: "Not all requirements will lead to test purposes due to the limitations imposed by the chosen type of testing, e.g., conformance or interoperability testing." — [TPLan paper](https://dl.ifip.org/index.html/db/conf/pts/testcom2007/SchulzWR07.pdf)

### Inferences
- **The measured suite's nine-field record maps essentially one-to-one onto this tradition**: `Reference` = RQ traceability (X.291 10.3/10.4, ETSI's Requirements Catalogue link); `Technology` + `Profile` = ICS-style applicability predicates, i.e. the "checklist of capabilities… can guide test selection" mechanism; `System under test` = the IUT role; `Purpose` = the TP proper; `Preconditions` = the `with { }` clause; `Test scenario` / `Expected results` = the `when { } / then { }` stimulus-response pair; the identifier taxonomy = the TSS group hierarchy. The suite is a TSS&TP document in 29119-3 clothing.
- **This reframes the completeness question.** In the 9646 tradition completeness is measured by X.291 clause 10.4 "Coverage", which is *requirement coverage against the Requirements Catalogue*, qualified by the explicit caveat that not all requirements yield test purposes. The tool's 3257 coverage items are an *input-space* coverage notion; the official suite's completeness notion is a *requirements-traceability* notion plus an *applicability* notion. A generator that wants to match the human suite must enumerate over `(requirement × applicability)` with requirement-coverage as the criterion, and only then use 29119-4 techniques to decide how many purposes a given requirement needs.
- **`perform all Common_X test cases` is the X.291 clause 11 / Annex D "generic test suite / generic test case" construct.** That is the published name for a parameterisable, technology-independent test case instantiated per technology — the exact mechanism the 27 composite references use. A generator that models this explicitly produces *one* generic family plus *n* instantiation references rather than n × m concrete cases.

### Gaps
- X.291 clause 10.4 "Coverage" and clause 11's actual text are paywalled; I have the clause titles from the ITU TOC but not the normative wording. Same for ISO/IEC 9646-2 Annex D on generic test cases. The report should mark the clause structure as verified and the clause contents as inferred from the titles plus secondary sources.
- The PICS-to-test-group mapping rules (how an ICS answer selects test groups) are in 9646-2 and 9646-7 and were not retrievable.

## Q5. Test-purpose templating, parameterisation, abstraction and suite factorisation — how many distinct artefacts must a generator actually produce?

### Takeaway
TPLan (ETSI ES 202 553, 2007) is the standardised, published model of exactly the templating the human suite exhibits: a fixed header/body skeleton, a *user-extensible domain vocabulary* declared once centrally, hierarchical `Group` structuring into a TSS, and `#include` for factorisation across writers — and the paper explicitly proposes mining recurring precondition and interaction patterns for reuse. Under this model a generator's output decomposes into a small vocabulary + a small set of purpose patterns + a large instantiation table, which is a far smaller artefact count than one prose test case per coverage item.

### Cited Findings
- **TPLan's skeleton (verbatim figure)**:
  ```
  -- test purpose header
  TP id: <string>
  < other test purpose headers (optional) >
  -- test purpose body
  with { <pre-conditions> }   -- optional clause
  ensure that {
    when { <stimulus> }
    then { <response> }
  }
  ```
  The header "provides a unique identifier… and, optionally, references to other useful information… These can include the requirement(s) covered by the test purpose, the type of test purpose, dependencies with other test purposes, and the tested role of the IUT." The body "specifies the specific initial IUT condition required for the test purpose to be valid and critical verdict criteria for a test — in the form of a stimulus and response". — [TPLan paper §3.1](https://dl.ifip.org/index.html/db/conf/pts/testcom2007/SchulzWR07.pdf)
- **Real header fields used in practice** (from the paper's dPMR and IPv6 examples): `TP id`, `summary`, `TP type` (conformance / interoperability), `RQ ref`, `IUT role` / `EUT role`, `config ref` (test architecture/configuration), `TD ref`. "almost all test purpose header lines are optional" — [TPLan paper §4](https://dl.ifip.org/index.html/db/conf/pts/testcom2007/SchulzWR07.pdf)
- **Six fundamental building blocks** from which every body is constructed: Entity, Event ("the measurable basis of a stimulus or response which may be parameterized with Values"), Value ("a literal constant; a numeric constant; a field or other container"), Unit, Condition, Word — [TPLan paper Table 2](https://dl.ifip.org/index.html/db/conf/pts/testcom2007/SchulzWR07.pdf)
- **Parameterisation is abstraction, deliberately partial**: "The definition of the SETUP event shows one parameter. That does not mean that in practice the message that this event represents only has one parameter. It means that **only this parameter is significant in determining whether the IUT fulfills the referenced requirement.** In test purposes, events are abstract representations of exchanged or observed information; **they are not complete message instances.**" — [TPLan paper §4](https://dl.ifip.org/index.html/db/conf/pts/testcom2007/SchulzWR07.pdf)
- **Factorisation mechanisms, named**: "TPLan offers two complementary mechanisms which are **grouping and inclusion**." `Group n / End Group n` builds a hierarchy; a TSS header collects them; `#include` inserts another TPLan file, used both to "maintain a single source of vocabulary extensions" and "to construct a complete TSS from separate group files developed by multiple test purpose writers" — [TPLan paper §3.3 "Arrangement of test purpose definitions", Figs 4–5](https://dl.ifip.org/index.html/db/conf/pts/testcom2007/SchulzWR07.pdf)
- **The vocabulary-saturation effect, measured qualitatively**: "We noticed that, independent of the project type, the user defined vocabulary initially grows quite rapidly during the specification of first test purposes. After that, however, **the need for new definitions levels off quickly.**" — [TPLan paper §4](https://dl.ifip.org/index.html/db/conf/pts/testcom2007/SchulzWR07.pdf)
- **Pattern mining is the paper's own proposal for factorisation**: checked test purposes "can be used as input to other forms of processing. One of these is the **identification of recurring patterns in preconditions and the interactions between entities.** Such patterns can be used in a variety of ways: 1. the identification of potentially reusable segments of test case specifications derived from the test purposes; 2. an assessment of test purpose variation; 3. an estimation of the possible complexity of the eventual test case specification; 4. an estimation of the effort likely to be required for implementing the eventual test specifications." — [TPLan paper §5](https://dl.ifip.org/index.html/db/conf/pts/testcom2007/SchulzWR07.pdf)
- **Suite-size datapoint**: "TPLan has already been used within ETSI to specify **more than a thousand test purposes** in the context of test development for the Internet Protocol version 6 (IPv6) and digital Public Mobile Radio (dPMR)" — [TPLan paper §1](https://dl.ifip.org/index.html/db/conf/pts/testcom2007/SchulzWR07.pdf). Same order of magnitude as the 907 measured.
- **Origin in patterns**: "The Test Purpose notation, TPLan, was conceived when investigating approaches to improving efficiency in the development of test specifications **based on patterns**. Here, it was realized that patterns could or should be identified much earlier than at the time of test case writing, i.e., when identifying test purposes." — [TPLan paper §1](https://dl.ifip.org/index.html/db/conf/pts/testcom2007/SchulzWR07.pdf)
- **What a generator from purposes cannot supply**: "there are many details which are not specified in test purposes but which are required for test case specification such as preamble implementation, complete message values, guarding against unexpected behaviour, postamble implementation" — [TPLan paper §5](https://dl.ifip.org/index.html/db/conf/pts/testcom2007/SchulzWR07.pdf)
- **Standardisation and adoption, honestly reported**: TPLan is ETSI ES 202 553 (2007), and "The use of TPLan as the means of specifying Test Purposes is optional but, if it is used, the requirements specified in the present document shall be met" — [ETSI ES 202 553](https://www.etsi.org/deliver/etsi_ES/202500_202599/202553/01.01.01_50/es_202553v010101m.pdf). **But** an ETSI STF report found "TPLan as such has not been decisively adopted as the notation of choice for the specification of test purposes at ETSI", that "a variety of 'dialects' have emerged which adopt certain notions from TPLan, yet do not strictly adhere to all principles defined in the TPLan standard", and that "the informal character of the notation causes potential inconsistencies and ambiguities in the specifications and corresponding maintenance overhead, and makes machine analysis and tool support difficult" — [ETSI STF 476 Task 4 Report (MTS/TDL)](https://docbox.etsi.org/STF/Archive/STF476_MTS_TDL2/Public/STF%20476%20-%20Task%204%20Report.pdf). ETSI's successor direction is TDL (Test Description Language).
- **ETSI practice uses proformas for TSS&TP**: ETSI TS 102 995 (2010) is "a proforma for the TTCN-3 reference test suite", whose annexes are the language ICS, the TSS&TP, a partial IXIT proforma and the TTCN-3 ATS; derivative specs state they "provide TSS and TP… following the pro forma" — [ETSI TS 102 950-2](https://etsi.org/deliver/etsi_TS/102900_102999/10295002/01.06.01_60/ts_10295002v010601p.pdf); [TS 102 995 listing](https://standards.globalspec.com/std/1286641/ts-102-995). ETSI TS 103 254 (XML/JSON Schema conformance) carries a **normative Annex A on test purposes with subclauses on naming convention, structure and format** — [ETSI TS 103 254 V1.5.1](https://www.etsi.org/deliver/etsi_ts/103200_103299/103254/01.05.01_60/ts_103254v010501p.pdf)
- **CTM's analogue of factorisation**: trees "can be grouped into 'compositions'", and the documented limitation is that "trees can become large without test decomposition" — [Wikipedia, CTM](https://en.wikipedia.org/wiki/Classification_Tree_Method)

### Inferences
- **The artefact count collapses by roughly an order of magnitude under the TPLan model.** 907 cases over 118 families with 112 distinct precondition blocks (the commonest shared by 154 cases) factorises into: a declared vocabulary (entities, events, values, conditions — the TPLan `def` layer, which the paper says saturates early), ~112 named precondition blocks, ~118 group headers, a handful of body patterns per check family, and 907 *instantiations*. The number of pieces of **prose a model must write** is therefore on the order of 100–250 (vocabulary + precondition blocks + patterns), not 907 and certainly not 3231. This is the strongest argument in the whole research set for changing the tool's generation unit: **one LLM call per pattern, not per coverage item.**
- The 27 `perform all Common_X` references are the genre's `#include` / generic-test-case mechanism operating at the suite level. Modelling them explicitly means the generator must emit a *composition graph*, not a flat list — and must be able to score itself on covering a referenced family by reference rather than by duplication. A flat generator cannot even represent, let alone match, those 27 cases.
- **Templating is why the deterministic/LLM split in the measured tool is misallocated.** The deterministic stage currently enumerates checks (where the humans were selective) and the LLM writes 3231 independent prose blocks (where the humans were templated). Inverting it — deterministic enumeration over `requirement × applicability × check-family`, LLM writing a small pattern library, deterministic instantiation — matches both the observed 112-precondition-block reuse and the TPLan paper's own proposed tooling direction.
- The ETSI STF 476 finding that TPLan's informality "makes machine analysis and tool support difficult" is a warning worth carrying into the report: a generator that emits structured purposes (fields, declared vocabulary, explicit parameters) is doing what ETSI itself concluded was missing, and TDL is the modern vehicle for it.

### Gaps
- No published quantitative study of test-purpose *factorisation ratios* (patterns per purpose, or purposes per pattern) in any real conformance suite. The TPLan paper proposes pattern mining as future work and reports no numbers. The measured 118/7.7/112 figures from the mDL suite may actually be a novel datapoint.
- ETSI TS 102 995 Annex B (the TSS&TP proforma text) and TS 103 254 Annex A (TP naming convention / structure / format) were not retrievable in text; I can cite that those normative annexes exist and what they are about, not their rules.
- TDL (ETSI ES 203 119 series) was not researched; if the report wants the modern standardised successor to TPLan, that is the obvious follow-up.

## Q6. Test-purpose granularity: how does the step count stay at ~2.4?

### Takeaway
The ~2.4-step figure is the documented, intended granularity of a *test purpose*: the tradition's rule is one purpose per requirement, and TPLan's own guidance is explicit that `when`/`then` must **not** be a complete test sequence but only the directly relevant stimulus and response — so a two-to-three-step purpose is the genre's norm, not an artefact of author laziness.

### Cited Findings
- **The granularity rule (verbatim)**: "**Each test purpose usually focuses on one specific requirement.**" — [TPLan paper §2](https://dl.ifip.org/index.html/db/conf/pts/testcom2007/SchulzWR07.pdf)
- **The anti-sequence rule (verbatim)**: "The keywords 'when' and 'then' **should not be misunderstood to require a complete specification of accurate test sequence(s). Stimulus and response in a test purpose should focus and isolate only the directly relevant parts of information** needed to assess if a requirement is indeed fulfilled by an IUT, for example, message types and critical information element values. Again, the level of information content and language used should be identical to the one of the requirement definition in the base specification." — [TPLan paper §3.1](https://dl.ifip.org/index.html/db/conf/pts/testcom2007/SchulzWR07.pdf)
- **Purposes are not steps**: "Test purposes provide an essential abstraction of a test that specifies what is to be tested without going into the details of how a test is to be implemented. **Test purposes are not test steps; they specify pass verdict criteria.** Test purposes are written using the language and terminology of the base specification(s) and are independent of any particular programming language, test system or platform" — [TPLan paper §2](https://dl.ifip.org/index.html/db/conf/pts/testcom2007/SchulzWR07.pdf)
- **Perspective rule**: "A test purpose body is usually written from the perspective of the IUT, i.e., pre-conditions refer to the required initial state of the IUT" — [TPLan paper §3.1](https://dl.ifip.org/index.html/db/conf/pts/testcom2007/SchulzWR07.pdf)
- **Audience rule that enforces brevity**: purposes "bridge the gap between original requirements and test case specification but also between technology experts (who are not necessarily test engineers), managers, and the test engineers"; at ETSI "test specifications are often reviewed and approved by standards working groups. These groups need to understand the requirements which are being tested **without having to read detailed test case specifications**" — [TPLan paper §2](https://dl.ifip.org/index.html/db/conf/pts/testcom2007/SchulzWR07.pdf)
- **Sequencing rule**: purposes "need to be developed, discussed and stabilized **prior to any test case specification**" — [TPLan paper §2](https://dl.ifip.org/index.html/db/conf/pts/testcom2007/SchulzWR07.pdf)
- **Corroboration of one-requirement-per-test as ETSI practice**: an ETSI presentation states conformance testing is "usually limited to one requirement per test"; an ETSI-linked 2010 presentation describes "one Test Case for each Test Purpose representing one Requirement from the Requirements Clause" — [ETSI workshop presentation](https://docbox.etsi.org/workshop/2007/200712_ECCONCERTATION/MUELLER_ETSI_eGRID_2007-12-06_SM.pdf); [ITU-D NGN testing centre presentation](https://itu.int/ITU-D/tech/OLD_TND_WEBSITE/network-infrastructure_OLD/NGNCenter_Kenya_Aug10/Files/NGNTestingCentre_Nairobi_Presentation_DAndreev_S5_R1.pdf)
- **But the mapping is not strictly 1:1 in all traditions**: a 2006 ITU-T workshop on the IPv6 testing framework allows that "one TP may test several Requirements, and one Requirement may spawn several TPs" — [ITU-T workshop slides](https://itu.int/dms_pub/itu-t/oth/06/02/T06020000020001PDFE.pdf)
- **Quality effect of structured writing**: "The extra effort spent in structured writing helped to reveal many problems or inconsistencies in the base specification prior to any test case specification or execution", and this was most apparent where "writers were experts in the technology but novices in testing"; automated syntax checking "gave a first level of assurance on test purpose quality" but "a manual check of test purposes was nevertheless still required to assure their correctness" — [TPLan paper §4](https://dl.ifip.org/index.html/db/conf/pts/testcom2007/SchulzWR07.pdf)

### Inferences
- **A 2.4-step scenario with 2.9 parallel expected results is a `when`/`then` pair plus a setup or teardown step** — a near-exact match to the TPLan body. The measured suite is therefore granular *by design rule*, and a generator should enforce the same constraint as a hard output schema rather than letting a model decide length: one requirement, one applicability predicate, one check, a lettered precondition block, 2–3 steps, 2–3 parallel expected results.
- The "purposes before cases, purposes readable by non-testers" rules explain why the official suite is prose-light and uniform: the audience is a standards working group voting on the document. A generator optimising for prose richness per item is optimising against the genre.
- The `one requirement per purpose` rule combined with `not all requirements yield purposes` (Q4) gives a *computable* completeness target for a generator: for each testable requirement in the extracted requirements catalogue, at least one purpose per applicable check family and per applicable Technology/Profile combination selected by the combination criterion. That is a requirement-coverage criterion, not an input-space criterion, and it is the one the official suite is actually measured against.

### Gaps
- No normative sentence found that *mandates* one requirement per test purpose; the ETSI sources treat it as convention ("usually focuses on", "usually limited to"), and the ITU-T IPv6 framework explicitly allows many-to-many. The report should present it as the tradition's strong convention, not a rule.
- No published guidance found that puts a numeric bound on steps per test purpose.

## Q7. Model-based testing coverage criteria, and what MBT case studies report for generated-vs-manual suite size and overlap

### Takeaway
The structural MBT criteria are a clean subsumption lattice (all-transitions subsumes all-states; transition-pair and bounded-path criteria sit above), and the strongest industrial evidence says the *model* is what buys fault detection, not the automation: generated and hand-written suites derived from the same model found equally many errors at equal size, while both beat suites written directly from requirements — but automated generation is dramatically cheaper and misses some fault classes manual tests catch.

### Cited Findings
- **Criteria and subsumption**: all-states requires every state of the model be visited at least once; all-transitions requires every transition be traversed at least once, and since every transition covers its source and target states, **all-transitions subsumes all-states**. One source calls all-transitions "the minimum coverage criterion" and another "the minimum to reach in practice" — [Chalmers DAT261 "Selecting Tests" lecture](https://www.cse.chalmers.se/edu/course.2016/DAT261/_downloads/08-Selecting-Tests-2016.pdf); [BME MBT course notes](https://www.tmit.bme.hu/sites/default/files/AG_MBT_2018.pdf)
- **Tool reality check**: "most of the commercial test generators tools are only able to satisfy slightly weak coverage criteria", with an example tool "only able to cover all-Transitions coverage criteria" — [JTEC review](https://jtec.utem.edu.my/jtec/article/download/2743/1801/7374)
- **Stronger criteria detect more**: a state-based-testing study found "all transition is not an adequate level of fault detection with more execution time compared to all transition pair (ATP) with length 4 (LN4)", and ranked "ATP with LN4 … the best among all coverage criteria" — [Coverage Criteria for State Based Testing](https://www.academia.edu/115351332/Coverage_Criteria_for_State_Based_Testing) (academia.edu hosting; treat as lower-tier)
- **Count example for a path criterion**: all-one-loop-paths coverage on an illustrative model produces "4*3 = 12 test cases" — [BME MBT course notes](https://www.tmit.bme.hu/sites/default/files/AG_MBT_2018.pdf)
- **Automotive network controller, ICSE 2005** (the closest match to generated-vs-manual): "Both automatically and manually derived model-based test suites detected significantly more requirements errors than hand-crafted test suites that were directly derived from the requirements"; "the number of detected programming errors did not depend on the use of models"; "Automatically generated model-based test suites detected as many errors as hand-crafted model-based suites with the same number of tests"; and **"a sixfold increase in the number of model-based tests led to an 11 % increase in detected errors"** — [Pretschner et al., "One evaluation of model-based testing and its automation", ICSE 2005, preprint](https://arxiv.org/pdf/1701.06815)
- **Train control / IEC 61131-3, Enoiu et al.** (coverage-directed generation vs industrial engineers' manual tests): "the use of an automated test generation tool does not result in better fault detection in terms of mutation score compared to manual testing"; "manual test suites more effectively detect logical, timer and negation type of faults, compared to automatically generated test suites"; generated suites "reached similar code coverage as manually created test suites, but in a fraction of the time (an average improvement of roughly 90 %)" — [MDH/MDU publication 4576](https://www.es.mdu.se/pdf_publications/4576.pdf)
- **29119-4 excludes MBT by design**: "other test practices such as model-based testing are not defined in this document because this document only describes techniques for designing test cases" — [29119-4:2021 preview, Introduction](https://assets.vde-verlag.de/iec-normen/preview-pdf/info_isoiecieee29119-4%7Bed2.0%7Den.pdf)
- **Test purposes as MBT coverage directives**: "When used in a model-based testing context, TPLan test purposes can be used in the definition of coverage criteria or testing directives for test generation from formal executable models. Here, the test purpose would define a path through model behaviour." The paper also warns that "A stimuli or response of a test purpose specification may correspond to only one state transition but also to a path or even multiple paths in the model" — [TPLan paper §5](https://dl.ifip.org/index.html/db/conf/pts/testcom2007/SchulzWR07.pdf)
- **Formal test-purpose-driven generation exists**: Jard & Jéron's TGV ("TGV: theory, principles and algorithms"), Tretmans' formal conformance-testing theory (PhD, Twente, 1992), Deussen & Tobies "Formal Test Purposes and The Validity of Test Cases" (FORTE 2002), and MSC-based test purpose specification (Grabowski, Hogrefe & Nahm, SDL'93), plus the UML 2.0 Testing Profile (OMG, 2003) — all cited as prior approaches to formalising test purposes that, per the TPLan authors, "have yet to be deployed successfully in industry" — [TPLan paper §1 and references](https://dl.ifip.org/index.html/db/conf/pts/testcom2007/SchulzWR07.pdf)

### Inferences
- **The "sixfold tests → 11 % more errors" figure is the most directly applicable published result to the measured 3257-items-for-13.8 % problem.** It says bluntly that scaling a generated suite within the same model yields sharply diminishing returns; coverage gains come from *extending the model*, not from enumerating more items over it. The tool's path forward is therefore to add classifications/techniques (syntax, state-transition, applicability), not to add rungs to the existing ladder.
- **The 44 behaviour/protocol-flow checks are the part of the official suite that needs a behavioural model at all.** For that slice, all-transitions is the published minimum criterion and transition-pair the published better one; everything else in the suite (presence, encoding, value, size — 817 of 907) is input-space/data coverage, where equivalence partitioning, boundary value analysis, syntax testing and combinatorial criteria apply and where no state machine is needed.
- The Enoiu finding that manual tests catch "logical, timer and negation type of faults" that generated tests miss is a useful calibration on ceiling: even a well-constructed generator should expect to miss a residue of the human suite, and claims of 100 % reachability should be treated sceptically.

### Gaps
- I found **no** case study reporting generated-vs-manual suite size *and* overlap side by side for all-states vs all-transitions, and none at all for a conformance test suite derived from a written standard. The ICSE 2005 and Enoiu studies are the closest and neither is standards-conformance. This is a real gap in the literature and should be stated as such.
- No source found for "all-definitions" / data-flow coverage criteria *over a data model* (as opposed to over code). 29119-4's data-flow clause (5.3.7) is structure-based, i.e. code-based, so it does not transfer to a data-model-heavy standard. Do not claim all-definitions applies here without further evidence.
- A blog claiming "40–60 % reduction in test creation time and 23 % more defects found" attributed to IEEE sources could not be verified and should not be used — flagged by the search as unattributable.

## Q8. Negative and invalid-input testing: systematic enumeration of invalid cases

### Takeaway
There are two published, mechanical mechanisms rather than model judgment: the category-partition `[error]` annotation (mark invalid choices, give each one test, do not cross them), and syntax testing — a declared grammar (29119-4 defines BNF as a term for precisely this) plus mutation of the grammar's productions, which modern research shows is the way to get *structurally near-valid* invalid inputs that a generator from the grammar alone will never produce.

### Cited Findings
- **29119-4 makes syntax testing normative and names the apparatus**: clause 5.2.4 "Syntax testing" with coverage clause 6.2.4, and term 3.1 "**Backus-Naur Form — formal meta-language used for defining the syntax of a language in a textual format**" — [29119-4:2021 preview](https://assets.vde-verlag.de/iec-normen/preview-pdf/info_isoiecieee29119-4%7Bed2.0%7Den.pdf)
- **The two goals of syntax-based testing**: "Tests are created with two general goals: cover the syntax in some way, and violate the syntax (invalid tests)" — [UWA CITS5501 lecture](https://teaching.csse.uwa.edu.au/units/CITS5501//lectures/lect05c--mutation.pdf)
- **Its coverage criteria**: "terminal symbol coverage, production coverage, and mutation testing", with emphasis on "the importance of creating both valid and invalid test cases" — [syntax-based testing course slides](https://www.scribd.com/presentation/870317214/7-Syntax-Based-Testing) (low-tier host; the UWA lecture above is the better citation for the valid/invalid framing)
- **Why generation from a grammar is not enough**: "grammar-based generation, by construction, will not yield such edge case inputs", and "the SUT parser may exhibit vulnerabilities that would only be triggered by slightly invalid inputs" — [Bendrissou, Cadar & Donaldson, TOSEM 2024 (Gmutator)](https://www.doc.ic.ac.uk/~afd/papers/2024/TOSEM.pdf)
- **The mutation operators, concretely**: typical grammar mutations are "changing some (non-)terminal of a grammar rule or removing some (non-)terminal in the rule"; Gmutator mutates the *grammar* fed to Grammarinator, while the G+M baseline applies byte-level mutations to generated inputs. Evaluation: "both Gmutator and G+M excel in generating edge case inputs, facilitating the detection of disparities between input specifications and parser implementations" — [Gmutator, TOSEM 2024](https://www.doc.ic.ac.uk/~afd/papers/2024/TOSEM.pdf); [project page](https://srg.doc.ic.ac.uk/publications/25-gmutator-tosem.html)
- **Staying structurally close to valid**: a parse-tree-swap mutation "randomly selecting two distinct parse subtrees that share that expansion as root and swapping them… ensures that the resulting mutated input is syntactically valid" — [Directed Grammar-Based Test Generation, arXiv 2508.01472](https://arxiv.org/pdf/2508.01472)
- **The category-partition answer**: `[error]` "marks invalid choices, which need only limited testing"; `[single]` marks choices needing only one test case; applying both took the FIND specification from 678 to 125 frames — [SFU course notes](https://coursys.sfu.ca/2023sp-cmpt-276-d2/pages/CategoryPartition). "All-pairs valid case testing" excludes error choices from the pairing entirely — same source.
- **Conformance-test categories include a negative class by construction**: Basic Interconnection Tests, capability tests, behaviour tests and conformance resolution tests — [BS EN 29646-1:1992 contents](https://infostore.saiglobal.com/en-gb/standards/bs-en-29646-1-1992-259292_saig_bsi_bsi_600732/)
- **Decision tables and cause-effect graphing are separate normative techniques** for the conditional cases: 29119-4 clauses 5.2.6 / 6.2.6 and 5.2.7 / 6.2.7 — [29119-4:2021 preview](https://assets.vde-verlag.de/iec-normen/preview-pdf/info_isoiecieee29119-4%7Bed2.0%7Den.pdf)

### Inferences
- **Syntax testing is the right home for the 257 type/encoding checks, and it is a completeness-bearing technique**: with a declared grammar for the encoding (CBOR/COSE/ASN.1/JSON Schema/ABNF — whatever the standard uses), *production coverage* and *terminal-symbol coverage* give a countable, auditable target, and the mutation operator set (alter terminal, alter non-terminal, delete terminal, delete non-terminal, swap subtree) gives a countable set of negative cases per production. That is a per-model-element expected count the tool currently has no analogue for: today it emits a flat `encoding invalid` rung per object, where syntax testing would emit one case per production × operator.
- **Decision tables and cause-effect graphing are the right home for the conditional presence checks.** Presence being `mandatory/optional/conditional` is a condition-combination problem, and decision-table coverage (one test per rule / per feasible condition combination) gives the count. The tool's `condition true` / `condition false` rungs are a degenerate 2-case approximation of a decision table; a real decision table over k conditions yields up to 2ᵏ rules before infeasible-rule elimination, which for a standard with multi-condition presence rules is where the official suite's conditional-presence cases come from.
- The combination of `[error]`-style marking with syntax-testing mutation is the published answer to the tool's inflation problem: negative cases are enumerated *systematically from a grammar* and then *not crossed* with the positive combination space.

### Gaps
- Beizer's own operator taxonomy from *Software Testing Techniques* (2nd ed., 1990) could not be sourced directly; the valid/invalid framing and the operator set are cited from course material and from modern grammar-mutation research instead. If the report wants the dated foundational citation, Beizer 1990 ch. 9 should be verified against the book.
- 29119-4's actual definition of a "syntax testing coverage item" and its coverage formula are behind the paywall (see Q3 gap). I can say the clause exists and what it is for; not what it counts.

## Q9. Which methods are generic across standards, and what a complete enumeration would look like

### Takeaway
Everything above is standard-agnostic: 29119-4 is explicitly domain-neutral, the 9646/X.291 TSS&TP framework is used by "protocol and profile specifiers" generally, TPLan was designed to be "as independent as possible from any specific application area", CTM "supports any type of system under test", and NIST's covering arrays are configuration-agnostic. The one thing that is *not* generic, and must be supplied per standard, is the **grammar of the encoding** and the **requirements catalogue**.

### Cited Findings
- 29119-4 "aims to provide stakeholders with the ability to design test cases for software testing in **any organization**" — [29119-4:2021 preview, Introduction](https://assets.vde-verlag.de/iec-normen/preview-pdf/info_isoiecieee29119-4%7Bed2.0%7Den.pdf)
- ISO/IEC 9646 "is widely used by protocol and profile specifiers to help them specify their conformance requirements unambiguously" — [ITU-T X.290 series](https://itu.int/dms_pubrec/itu-t/rec/x/T-REC-X.290-198811-S!!TOC-HTM-E.htm)
- TPLan: "Another design criterion was to keep the core notation as independent as possible from any specific application area and testing technology while making it easily extensible. **This opens TPLan to a wide range of applications from, for example, telecommunication to civil engineering.** It also allows it to be used in conjunction with both suite-based and model-based testing." — [TPLan paper §2](https://dl.ifip.org/index.html/db/conf/pts/testcom2007/SchulzWR07.pdf)
- TPLan has been applied to an IETF RFC (RFC 2460, IPv6) and to an ETSI radio standard (TS 102 490, dPMR) with the same notation — [TPLan paper §§1, 4](https://dl.ifip.org/index.html/db/conf/pts/testcom2007/SchulzWR07.pdf)
- CTM "works on any type of system under test, including hardware, software, embedded systems, and user interfaces" — [Wikipedia, CTM](https://en.wikipedia.org/wiki/Classification_Tree_Method)
- ETSI applies the same TSS&TP pipeline to XML and JSON Schema conformance (TS 103 254) as to protocols — [ETSI TS 103 254 V1.5.1](https://www.etsi.org/deliver/etsi_ts/103200_103299/103254/01.05.01_60/ts_103254v010501p.pdf)
- 29119-4 Annex A maps techniques to the **eight ISO/IEC 25010 quality characteristics**, i.e. technique selection is driven by quality characteristic, not by domain — [29119-4:2021 preview](https://assets.vde-verlag.de/iec-normen/preview-pdf/info_isoiecieee29119-4%7Bed2.0%7Den.pdf)
- Risk-based technique selection is the standard's own answer to "which techniques apply here": "Risk-based testing can be used to determine the set of techniques that are applicable in specific situations" — [29119-4:2021 preview, Introduction](https://assets.vde-verlag.de/iec-normen/preview-pdf/info_isoiecieee29119-4%7Bed2.0%7Den.pdf)
- NIST warns that modelling, not generation, is the hard part: "input space modeling can be a significant undertaking, and needs to be carefully managed" — [NIST/ICST 2012 ACTS case study](https://csrc.nist.gov/pubs/conference/2012/04/21/combinatorial-testing-of-acts-a-case-study/final)
- CTM's documented weakness is the same one: "**No algorithm guides the selection of aspects**" — [Wikipedia, CTM](https://en.wikipedia.org/wiki/Classification_Tree_Method)

### Inferences
- **A generic, citable enumeration architecture that would match the official suite's shape**, assembled entirely from the sources above:
  1. **Requirements catalogue** (ETSI/X.291 clause 9; 29119-4 clause 5.2.12 requirements-based testing). Completeness criterion: requirement coverage, with the explicit allowance that not all requirements yield purposes.
  2. **Classification tree** (29119-4 5.2.2) whose classifications are the object, the check family, the Technology tag and the Profile — legitimate because CTM admits preconditions and environment states as classifications.
  3. **Per-check-family technique**: presence/conditional → equivalence partitioning (5.2.1) + decision table testing (5.2.6); encoding → syntax testing (5.2.4) with a declared BNF, production/terminal coverage and grammar-mutation negatives; value and size → equivalence partitioning (5.2.1) + boundary value analysis (5.2.3); behaviour/flow → state transition testing (5.2.8) at all-transitions minimum, or scenario testing (5.2.9); plus sequence-covering arrays for ordering.
  4. **Combination criterion over the tree**: base-choice (count `1 + Σ(Bᵢ − 1)`) as the default, pairwise over applicability tags, with CPM-style `[error]`/`[single]`/`[if]` constraints — not all-combinations.
  5. **Suite structure and factorisation**: TSS groups, a declared vocabulary, named precondition blocks, generic/common families referenced rather than duplicated (X.291 clause 11, TPLan grouping + `#include`).
  6. **Output granularity**: one requirement, one check, 2–3 steps, parallel expected results, per the TPLan `with/when/then` rule.
- The two things no method supplies and that therefore determine whether any of this works: the **encoding grammar** (without it, syntax testing — the technique covering 257 of 687 official tests — cannot run) and the **aspect/classification selection** (CTM and NIST both name this as the unautomated step). The report should say plainly that the literature's consistent verdict is that *modelling is the bottleneck, enumeration is not.*

### Gaps
- No published generator was found that targets the TSS&TP genre specifically from a natural-language standard. The closest published direction is the TPLan paper's own proposal for "generation of test specification stubs" from structured test purposes, which it describes as future work.
- ETSI TDL (ES 203 119 series), the standardised successor the STF 476 report points to, was not researched and is the most obvious follow-up for "the modern standardised artefact format for this genre".
