# Evaluation of tpg against ISO/IEC TS 18013-6 test cases

Date: 2026-09-21. Model: gemma4:31b via Ollama Cloud. Tool version: master at 1bab20c.

## Setup

- **Standard under test:** `tests/fixtures/iso_18013_5.pdf`, which is **ISO/IEC DIS 18013-5:2020(E)**, the draft international standard, 126 pages.
- **Ground truth:** the three appendices of ISO/IEC TS 18013-6:2025 (Common and certificate tests, mDL tests, mDL reader tests), 727 pages. Every official test case has a fixed layout (Test case ID, System under test, Purpose, Reference, Technology, Profile, Preconditions, Test scenario, Expected results), which a rule-based parser (`eval/parse_18013_6.py`) turned into `eval/ground_truth.json`.
- **Run:** `tpg generate tests/fixtures/iso_18013_5.pdf` with no clause filter, output `eval/iso_full.json`.
- **Metrics:**
  - *Coverage (recall):* for each official test case that cites an 18013-5 clause, retrieve the five closest generated test cases by weighted token overlap over all 428 generated cases, then ask the same model whether any of them verifies the same check (`eval/judge.py`). Strict criterion: same data item or behaviour, same condition, same expected outcome.
  - *Precision (validity):* a random sample of 60 generated test cases judged against the clause excerpt they came from on three booleans: grounded in the requirement, actionable, expected result correct (`eval/precision.py`).
  - Ingest and extraction diagnostics from the run log and the clause list.

The `eval/` directory is gitignored because it contains ISO text.

## Why coverage is low

The generated cases are mostly valid, so the gap is in what reaches generation and at what granularity. Five causes, in decreasing weight.

**1. Edition mismatch (evaluation confound, not a tool defect).** The fixture is the 2020 DIS; the tests cite the 2021 published edition. Numbering differs (DIS 8.2.1.1.2.2 "mDL Response" is 2021's 8.3.2.1.2.2; DIS 9.2.x security clauses are 2021's 9.1.x), and content differs in places. The judge compares content, not numbers, so the coverage figure is meaningful, but some official tests target text that is not in the draft.

**2. Whole-batch rejection at extraction discards the most-tested clauses.** One invalid draft rejects a clause's entire batch, three times, then the clause becomes a gap. The 14 gapped clauses include the mDL data table (DIS 7.4.1), MSO signing (9.2.2.4) and session encryption (9.2.1.4). A lower bound of 196 drafts were discarded in gapped clauses (excluding the mis-segmented clause 5.2), against 215 accepted. The rejections themselves were:

| Cause | Gaps |
|---|---|
| Modality check: "should not", "shall never", "may not" sentences. The schema has no `should_not`, and the negation rule (correctly) refuses `should` on a "should not" quote, so these 32 sentences in the standard can never pass | 9 |
| Quote not verbatim: soft hyphens (U+00AD, 33 in clause text), page headers and footers inside clause text (120 fragments), model paraphrase | 5 |

**3. Ingest misses half the clause structure of this PDF.**
- ISO prints a dotted clause number alone on a line and the title on the next. 254 such headings exist; 164 have titles starting lowercase ("mDL Reader", "nameSpace", "issuing authority infrastructure"). The uppercase-title rule, added to stop RFC table rows, rejects them: 45 distinct clause ids are lost.
- Annex headings ("Annex B", "B.1", "C.2.3") are not recognised (147 lines), so the five annexes are never split.
- A table in Annex B listing RFC 5280 section numbers ("5.2", "5.2.1") produces a false heading "5.2" that then absorbs 122 KB, everything from page 71 to the end, into one clause; extraction on it failed and gapped.
- Running page headers and footers are not stripped and end up inside clause text and inside quotes.

**4. Granularity mismatch.** The official suite has one test per data element and per structural check (90 tests for the data element table alone, one per element and encoding rule). The tool produces one nominal plus negatives per modal-verb sentence of prose. Tables are flattened to text and a single "shall" sentence governing a table yields one requirement, not one per row. Even a perfect run of the current design would not reach the official granularity on table-driven clauses.

**5. Retrieval and judge strictness (measurement).** The judge saw only the five lexically closest candidates and applied a strict same-check criterion. Some matches may be missed; the sample of reasons suggests the misses are real (candidates test broader or different properties), but the 4.2 % should be read as a lower bound within a few points.

## What to change, in order of expected gain

1. **Per-draft acceptance in extraction.** Keep the valid drafts of a batch and retry or gap only the invalid ones. Cheapest change with the largest effect: it recovers the ~200 discarded drafts and the three biggest clauses.
2. **Add `should_not` (and treat "shall never", "may not") in the modality model and checks.** Nine of fourteen gaps.
3. **Ingest for ISO layout:** accept lowercase titles when the heading came from a number-only line join; recognise annex numbering (`Annex X`, `X.n.n`); strip repeating page headers and footers; remove soft hyphens; require that a heading's number sequence be plausible relative to the previous heading (rejects the RFC-5280 table numbers).
4. **Table-aware extraction.** Detect tables (pymupdf `find_tables`) and emit one requirement per row when the governing sentence is a "shall"; this is the only route to the official granularity on data-model clauses.
5. **Use the 2021 edition as the fixture** for any further comparison against 18013-6; the draft confounds the numbers.
6. **Negative-case prompt:** forbid "verify that X is not required" as a negative case; a negative case must observe a rejection or error.
