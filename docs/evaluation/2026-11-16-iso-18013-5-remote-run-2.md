# Second remote run on ISO/IEC DIS 18013-5: analysis

Analysed 2026-11-16 from `eval/eval_remote_2/eval/`. Plan generated 2026-10-17 with `qwen3.8:27b`
on a local Ollama 0.35.0, tool at `master` (`cdf61ff`, the conformance-methodology merge). Compared
throughout with the first remote run, `eval/eval_remote_1/eval/` (2026-10-03, `gemma4:31b`), and
with the baseline of `2026-09-21-iso-18013-5-evaluation.md`.

## Verdict in three lines

1. **The run produced no test case.** All 2334 generation batches failed all three attempts:
   0 test cases, 7978 generate-stage gaps. The LLM judge (0 of 687) and the precision sample (0 of 0)
   are therefore void, not low.
2. **Everything before generation improved, and it is measurable without a model.** The structural
   match of the official suite went from 22.5 % to 34.9 % on the comparable basis (36.9 % on the
   run's own basis), objects from 921 to 1590, and the plan now carries 1989 ICS items.
3. **The run cannot be compared on cost or on case quality.** The model changed between the two
   runs, the wall time was 126 hours, and there are no cases to judge. A rerun is owed.

## The generation failure

Every line of the generate stage in `plan.log` reads `<source>: 0/N cases (GAP)`, from the first
source to the last, batches of one item included. Every one of the 7978 gaps carries the same
reason, `no test case was returned for this coverage item`.

What the artefacts establish:

- **It is not the case checks.** A case rejected by `check_test_case` leaves its own reason in the
  gap. `NO_CASE` is written only when no entry with a requested id ever came back: either every call
  raised an `LLMError` (timeout, unparseable reply, schema mismatch), or the reply held no case under
  a listed id.
- **It is not the model being unreachable or unable to follow a schema.** The extract and model
  stages of the same process produced 810 requirements and 1438 prose objects, and the judge
  afterwards answered 687 schema-bound calls in 1296 s.
- **It is not a 600-second timeout on every call.** About 7000 attempts in at most 453928 s is under
  65 s per attempt on average.

What they do not establish is which of the remaining causes it was, because **the gap reason discards
the `LLMError` text**: in `generate_source` a failed call sets `failures` for the next prompt and
never reaches `reasons`, so the error messages were dropped and replaced by one constant. The sidecar
`plan.json.cases.jsonl`, which would have shown the same thing live, is deleted once the plan is
written, and this plan was written.

The run then spent 126 hours where the three-minute scoped check of `RUNNING.md` section 5, run with
the same model, would have shown `0/N cases` on its first source.

## What else is wrong with the artefacts

- `run.out` is byte-identical to run 1's file. It is a stale copy and documents nothing about run 2.
- The judge made 687 calls against zero candidates; 685 of its reasons read "No candidate test cases
  were provided". Its 0 % is not a coverage figure.
- The summary's "the two agree on 374 of 591 cases (63.3 %)" is an artefact of the same void: with
  the judge at zero, agreement is just the count of cases the structural matcher did not match.
- `precision_results.json` is `[]`; the summary reports it as missing.
- The exit code of the generate step, the GPU and the values of `OLLAMA_CONTEXT_LENGTH`,
  `OLLAMA_KEEP_ALIVE` and `OLLAMA_TIMEOUT` in force were not sent back (`RUNNING.md` section 10), and
  they are what the timing question above needs.

## What to do, in order

1. **Keep the `LLMError` text in the generate gap reason.** A few lines in `generate_source`; without
   it the next failed run is as opaque as this one.
2. **Reproduce on two clauses with `qwen3.8:27b`** (`--clauses 8.2.1.1,9.2.2.4`, section 5 of
   `RUNNING.md`) and read the reason. Minutes, not days.
3. **Stop a run that is producing nothing.** Abort generation after some number of consecutive
   sources with zero cases, and have `run.sh` skip the judge and the precision sample when the plan
   has no test case.
4. **Rerun in full, and say which model.** With `gemma4:31b` the result is comparable with run 1 and
   isolates the tool; with `qwen3.8:27b` it is a model comparison. One run cannot be both.
5. Only then return to coverage: the behaviour family, the size family, and clauses 9.2.2 and 9.3.2.
